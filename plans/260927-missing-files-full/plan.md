# План: Агрегированный анализ отсутствующих архивов аккаунтов

## Описание

Создать отдельный диагностический скрипт `app/missing_files_full.py`, который расширяет проверки `missing_files_alt.py` агрегированным сравнением timestamp альтернатив и владельцев записей, ссылающихся на них. В конце отчёта независимо показать распределение групп дубликатов `account.number` по размеру и количество аккаунтов с отсутствующим точным файлом в этих группах. Скрипт предназначен только для исследования проблемы и не восстанавливает данные.

## Цель

Получать компактный, арифметически согласованный отчёт для БД с более чем 400 000 аккаунтов, позволяющий различить аккаунты с более новыми, более старыми и обоими видами альтернатив. Отдельная завершающая сводка должна показывать масштаб дублирования номеров и отсутствующих точных файлов без расширенного анализа дубликатов.

## Контекст

По предоставленному пользователем результату `missing_files.py` проверено 415 636 непустых `file_name`, у 25 951 аккаунта точный файл отсутствует, у 25 659 из них найдены альтернативы, у 292 альтернатив нет. Текущий `app/missing_files_alt.py` индексирует архивы по префиксу и проверяет точное присутствие альтернативного имени среди `file_name` БД, но не получает `number` и `user_id` и сохраняет только префиксы проблемных аккаунтов. `AccountCRUD.list_archive_files()` исключает записи без `file_name`, поэтому не подходит для полного анализа дубликатов. После обсуждения пользователь ограничил блок дубликатов группировкой по числу повторений, подсчётом пустых номеров и проверкой точных файлов, исключив из этого блока timestamp, альтернативы и сравнение владельцев.

## Требования

### Функциональные требования

1. Новый скрипт запускается как файл и как модуль, использует настройки подключения приложения и `--upload-dir`; каталог по умолчанию — `upload/wa` рядом со скриптом, независимо от рабочей директории. Основной рекомендуемый запуск — внутри работающего контейнера `api`.
2. Выборка охватывает все аккаунты всех пользователей и статусов, включая записи с пустыми `number` и `file_name`. Общая сводка разделяет все записи, записи без `file_name`, записи с заполненным `file_name`, существующие и отсутствующие точные файлы.
3. Основной анализ альтернатив выполняется только для аккаунтов с заполненным, но отсутствующим точным файлом, по правилам существующих скриптов. Альтернативы ищутся непосредственно в каталоге архивов по равному префиксу до первого `_` и окончанию `.tar.gz`, без рекурсии и поиска по `account.number`.
4. Timestamp исходного имени и альтернатив сравниваются численно; результат агрегируется по исходным аккаунтам в пять непересекающихся категорий, описанных ниже. Дополнительно выводятся пересекающиеся показатели «есть хотя бы одна более новая альтернатива», «есть хотя бы одна более старая альтернатива» и их пересечение.
5. Сохраняются показатели уникальных альтернативных файлов с точным совпадением полного имени в `account.file_name` и без такого совпадения. Повторы ссылок и повторное использование одного альтернативного имени разными проблемными аккаунтами не увеличивают счётчик уникальных файлов.
6. В основном анализе альтернатив сравнивается `user_id` исходного аккаунта с владельцами точных ссылок на альтернативы. Принадлежность агрегируется по аккаунтам без вывода списков пользователей, аккаунтов или файлов; семантика четырёх категорий определена ниже.
7. Дубликаты непустых `account.number` определяются независимо по всей выборке. В последнем аналитическом блоке для каждого размера группы от двух записей выводятся число групп, число аккаунтов и число аккаунтов с заполненным, но отсутствующим точным файлом; отдельно указывается количество аккаунтов с пустым номером.
8. В блоке дубликатов не выполняются поиск альтернатив, сравнение timestamp, сравнение `user_id` или восстановление ссылок. Проблемные аккаунты из групп дубликатов участвуют в основном анализе на общих основаниях, но отдельного повторного анализа альтернатив для них нет.
9. Консольный вывод содержит только агрегаты, единицы подсчёта и пояснения; объём вывода не растёт пропорционально числу аккаунтов или файлов. В интерактивном терминале показывается прогресс, при перенаправлении вывода нет управляющих последовательностей; диагностические ошибки не выдаются за успешный итоговый отчёт.
10. БД и архивы не изменяются. Ошибка чтения хранилища или БД прерывает диагностику с ненулевым кодом завершения, а сессия и engine освобождаются как при успехе, так и при ошибке или отмене.

### Нефункциональные требования

1. Использовать Python 3.11 и имеющиеся зависимости; SQL изолирован в локальном read-only-репозитории внутри нового скрипта, без изменения CRUD-модулей сервиса. Дисковый обход и файловые проверки выполняются вне event loop через `asyncio.to_thread()`.
2. Читать БД порциями по 1000 строк через keyset-пагинацию, выбирая только необходимые колонки, без полной загрузки ORM-объектов, связанных сущностей и запросов на каждую альтернативу или группу дубликатов.
3. Каталог индексируется один раз; в памяти хранятся компактные индексы и проблемные записи, а не все пары сравнений. Не проверять каждую альтернативу каждого аккаунта повторными обращениями к диску и не строить декартово произведение всей БД и каталога.
4. Единственный новый файл в репозитории — `app/missing_files_full.py`; разрешено также обновление этого плана. Все существующие модули сервиса, включая CRUD, старые скрипты, API, модели, конфигурацию и зависимости, должны оставаться без изменений, подтверждённых через `git diff`.
5. Проверки не обращаются к реальной БД, не используют production-секреты и не создают файлы в рабочем хранилище; внешние зависимости заменяются моками. Новые тесты и файловые фикстуры размещаются во временном каталоге вне рабочего дерева, без добавления тестовых файлов в репозиторий.

## Технические детали реализации

- Определить внутри `app/missing_files_full.py` локальный read-only-репозиторий `FileAuditRepository` на основе существующего `AccountCRUD` и его метод `list_file_audit_rows()` с типизированными строками `id`, `number`, `user_id`, `file_name`, сортировкой по убыванию `id` и курсором `before_id`. Репозиторий, контракт строки и SQL находятся только в новом файле; модуль `app/crud/account.py` и его методы не изменяются.
- Переиспользовать безопасную проверку из `app/utils/account_files.py` и подходящие чистые функции существующих скриптов; новый скрипт не должен импортировать API-роутеры, lifespan или инициализацию БД.
- При обходе БД накапливать независимо общие счётчики, размеры групп непустых номеров и количество отсутствующих точных файлов по каждому номеру; для основного анализа сохранить компактные данные только проблемных аккаунтов и владельцев точных ссылок на имена из дискового индекса.
- После завершения выборки сопоставить проблемные аккаунты с индексом альтернатив, чтобы результат не зависел от порядка встречаемости ссылок в порциях; для каждого префикса подготовить минимум и максимум корректных timestamp и множество владельцев ссылок, достаточные для классификации аккаунтов без хранения всех пар.
- Итоговую сводку дубликатов сформировать из агрегатов по всем номерам с числом записей не менее двух, используя уже выполненные точные файловые проверки, а не повторный поиск альтернатив или отдельные запросы на каждую группу.
- Разделить в новом модуле чистую классификацию, асинхронный сбор данных и форматирование отчёта; ошибки явно доводить до CLI с контекстом этапа, не раскрывая пароль или полный DSN.

## Правила агрегации

### Область исходных данных и файловые проверки

- `file_name IS NULL` и `file_name == ''` означают отсутствие имени, а не отсутствие указанного архива. Строка из пробелов остаётся непустым именем, как в существующей выборке; имена не обрезаются и не нормализуются.
- Для заполненного имени действуют существующие правила `account_file_exists()`: файл должен разрешаться внутри каталога хранилища и быть файлом; каталоги, битые ссылки и пути наружу не считаются существующим архивом. Символьная ссылка на файл внутри хранилища допускается.
- Недоступность самого каталога, ошибки доступа и I/O, цикл символьных ссылок не превращаются в счётчик отсутствующих архивов. Проверка заканчивается ошибкой, включая случай пустой БД при недоступном хранилище.
- Альтернативный префикс извлекается именно из исходного `file_name`, а не из `account.number`; это сохраняет возможность анализа записей с пустым или несогласованным `number`. Пути и имена без непустого префикса до `_` не участвуют в сопоставлении префиксов.
- Полное имя альтернативы сравнивается с `file_name` БД буквально: без обрезания пробелов, изменения регистра, разрешения путей, `LIKE` или приведения к basename.

### Timestamp и единица подсчёта «аккаунт»

Timestamp разбирается из простого имени вида `<prefix>_<timestamp>.tar.gz`: после первого `_` и до точного окончания `.tar.gz` должны находиться только десятичные ASCII-цифры. Значение интерпретируется как целое число секунд Unix, без фиксированной длины, автоматического перевода миллисекунд и использования `mtime`; ноль и ведущие нули допустимы. Отрицательные значения, дроби, знаки, пробелы, дополнительные `_`, неподходящий суффикс и ошибки преобразования в целое дают неразбираемый timestamp, а не аварийное завершение.

Нестандартное имя может оставаться найденной альтернативой по прежним правилам поиска, но не участвовать в числовом сравнении. Для каждого проблемного аккаунта с хотя бы одной альтернативой вычисляются признаки наличия меньшего, большего и равного корректного timestamp относительно исходного; при неразбираемом исходном timestamp все сравнения этого аккаунта недоступны.

| Категория аккаунта | Условие |
|---|---|
| Есть более новые, нет более старых | Есть больший timestamp и нет меньшего. Равные и неразбираемые альтернативы не исключают эту категорию. |
| Есть более старые, нет более новых | Есть меньший timestamp и нет большего. Равные и неразбираемые альтернативы не исключают эту категорию. |
| Есть и более новые, и более старые | Обнаружены оба направления сравнения. |
| Нет старее/новее, но есть равный timestamp | Больших и меньших значений нет, хотя бы одно корректное значение равно исходному. |
| Нет доступных сравнений timestamp | Нет ни одного корректного сравнения с исходным timestamp. |

Аккаунты без альтернатив учитываются отдельно и не входят в эти пять категорий. Наличие нескольких альтернатив одного направления не увеличивает число аккаунтов; один альтернативный файл может давать разные результаты для разных исходных аккаунтов.

Дополнительно выводится предупреждающий счётчик аккаунтов с альтернативами, у которых не удалось разобрать исходное имя или хотя бы одно альтернативное имя. Это пересекающийся показатель качества данных, а не шестая категория: он не должен скрывать случаи, когда часть сравнений выполнилась успешно, а часть нет.

Равенство timestamp при разных именах возможно из-за нестандартного числового представления, например ведущего нуля. Само по себе оно не означает тождество содержимого архивов; при обычном каноническом именовании и стабильном хранилище у отсутствующего исходного файла равной по имени альтернативы не ожидается.

### Ссылки в БД и `user_id` в основном отчёте

Сначала отдельно считаются уникальные альтернативные имена, участвующие хотя бы в одном проблемном аккаунте: всего, с точной ссылкой в БД, без точной ссылки. Количество записей с одним и тем же именем не влияет на этот файловый счётчик.

Для агрегирования по аккаунтам рассматривается объединение владельцев всех точных ссылок на все его альтернативы. Сравнение выполняется с `user_id` исходного проблемного аккаунта, а не с текущим пользователем приложения:

| Категория аккаунта | Условие |
|---|---|
| Ни одна альтернатива не указана в БД | Точных ссылок нет ни на одну альтернативу аккаунта. |
| Ссылки только того же пользователя | Хотя бы одна ссылка есть, и все владельцы найденных ссылок равны исходному `user_id`. |
| Ссылки только других пользователей | Ссылки есть, но среди их владельцев нет исходного `user_id`. |
| Ссылки и того же, и других пользователей | Среди владельцев есть исходный `user_id` и хотя бы один другой. |

Категории непересекающиеся и в сумме дают число аккаунтов с альтернативами. Они не означают, что каждый альтернативный файл имеет ссылку: отдельно вывести число аккаунтов, у которых есть хотя бы одна альтернатива без точной ссылки в БД.

Для связанного отчёта представить эти четыре категории колонками, а пять категорий timestamp — строками одной таблицы; каждая ячейка считает исходные аккаунты, не файлы и не пары. Принадлежность в такой таблице относится ко всему набору альтернатив аккаунта, а не обязательно к тому файлу, который дал признак «новее» или «старее»; это пояснение обязательно выводится и запрещает трактовать ячейку как рекомендацию по замене.

### Независимая сводка дубликатов в конце

1. Группировать все аккаунты по точному значению непустого `account.number`, не ограничивая `user_id`, статус или заполненность `file_name`.
2. `NULL`, пустую строку и строки только из пробелов учитывать общим числом аккаунтов с пустым номером и исключать из групп дубликатов. Остальные номера не нормализовать: например, `'221'`, `'0221'` и `'221 '` являются разными ключами.
3. Для каждого размера `k >= 2` вывести количество групп, число аккаунтов `k × количество групп` и сумму отсутствующих точных файлов у аккаунтов этих групп. Записи без `file_name` входят в размер группы, но не в счётчик отсутствующих указанных файлов.
4. Показать итоги по всем размерам и количество аккаунтов с пустым номером. Если дубликатов нет, явно показать нулевой итог.
5. Не добавлять в этот блок разбиение по владельцам, наличие альтернатив, сравнение имён между дубликатами или сравнение timestamp. Он является последним аналитическим блоком, после него допустимы только время работы и общие предупреждения.

## Макет консольного отчёта

Все числа ниже демонстрационные и не являются результатами сканирования сервера. Рабочий скрипт выводит подписи счётчиков и короткие пояснения к каждому блоку, но не списки аккаунтов, номеров, файлов или пользователей.

### 1. Общая проверка

| Показатель | Аккаунтов |
|---|---:|
| Всего в БД | 10 000 |
| Без `file_name` | 100 |
| С заполненным `file_name` | 9 900 |
| Точный файл существует | 9 600 |
| Точный файл отсутствует | 300 |

### 2. Альтернативы и timestamp

| Показатель | Аккаунтов |
|---|---:|
| Альтернативы не найдены | 60 |
| Альтернативы найдены | 240 |
| Есть более новые, нет более старых | 110 |
| Есть более старые, нет более новых | 70 |
| Есть оба направления | 40 |
| Нет старее/новее, но есть равный timestamp | 0 |
| Нет доступных сравнений timestamp | 20 |

Хотя бы одна более новая альтернатива есть у 150 аккаунтов, хотя бы одна более старая — у 110, пересечение — 40 аккаунтов. Числа 150 и 110 нельзя складывать как непересекающиеся категории. Наличие неразбираемых имён сопровождается отдельным предупреждением о неполноте сравнений.

### 3. Уникальные альтернативные файлы

| Показатель | Файлов |
|---|---:|
| Уникальных альтернативных архивов | 400 |
| Есть точное совпадение `file_name` в БД | 350 |
| Нет точного совпадения `file_name` в БД | 50 |

### 4. Timestamp и владельцы ссылок — аккаунты, не пары

| Категория timestamp аккаунта | Ссылок нет | Только тот же пользователь | Только другие | Тот же и другие | Всего |
|---|---:|---:|---:|---:|---:|
| Есть более новые, нет более старых | 20 | 70 | 15 | 5 | 110 |
| Есть более старые, нет более новых | 10 | 40 | 15 | 5 | 70 |
| Есть оба направления | 5 | 20 | 10 | 5 | 40 |
| Нет старее/новее, есть равный timestamp | 0 | 0 | 0 | 0 | 0 |
| Нет доступных сравнений timestamp | 5 | 10 | 5 | 0 | 20 |
| Итого | 40 | 140 | 45 | 15 | 240 |

Владельцы определены по всем альтернативам аккаунта. Например, более новая альтернатива может не иметь ссылки, а ссылка того же пользователя может относиться к более старой: таблица не утверждает, что один конкретный файл одновременно удовлетворяет всем признакам. Число аккаунтов хотя бы с одной альтернативой без ссылки выводится отдельно и может быть больше 40, поскольку у аккаунта одновременно могут существовать альтернативы со ссылками и без них.

### 5. Дубликаты `account.number` — последний аналитический блок

| Размер группы | Групп | Аккаунтов | С отсутствующим точным файлом |
|---|---:|---:|---:|
| По 2 одинаковых номера | 10 | 20 | 4 |
| По 3 одинаковых номера | 4 | 12 | 3 |
| По 4 одинаковых номера | 1 | 4 | 1 |
| Итого | 15 | 36 | 8 |

Аккаунтов с пустым номером: 5. Дубликаты найдены по всей БД; в этом блоке проверяются только точные пути из непустых `file_name`, без альтернатив и timestamp. Восемь отсутствующих файлов здесь относятся к аккаунтам, уже включённым в основной счётчик 300, и не прибавляются к нему.

## Проверки и инварианты

### Арифметика

- Все аккаунты = без `file_name` + с заполненным `file_name`.
- С заполненным `file_name` = точный файл существует + точный файл отсутствует.
- Точный файл отсутствует = без альтернатив + с альтернативами.
- С альтернативами = сумма пяти непересекающихся категорий timestamp = сумма всех ячеек матрицы timestamp/владельцев.
- Есть новее = есть новее без старее + оба направления; есть старее = есть старее без новее + оба направления. Их пересечение равно категории «оба направления».
- Уникальные альтернативы = с точной ссылкой + без точной ссылки.
- Для размера `k`: аккаунтов в строке = `k × групп`; отсутствующих указанных файлов не больше числа аккаунтов в строке.
- Итог отсутствующих файлов среди дубликатов не превышает основное число проблемных аккаунтов и не прибавляется к нему повторно.
