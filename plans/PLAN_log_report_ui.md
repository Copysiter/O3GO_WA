# План: Отдельный HTML-отчет по логам и endpoint открытия

## Цель
- Построить новый отчёт для истории изменений статусов и событий на основе `Log` и обеспечить отдельный точку доступа, которая возвращает HTML-страницу, не меняя текущий `account_history_report`.
- Обеспечить повторное использование существующих источников журнала (`app/services/log.py`, `app/crud/log.py`) и контрактов фильтрации API логов (`app/api/v1/logs.py`) для консистентности.

## Требования

### Функциональные
1. Сохранять текущий эндпоинт `GET /ext/api/v1/account/report` без изменений поведения.
2. Добавить отдельный HTML-отчёт, представляющий историю событий из `log` и покрывающий события, которые реально пишутся в системе (`account.create`, `account.update`, `account.status`, `session.create`, `session.update`, `session.status`, `message.create`, `message.update`, `message.status`).
3. Добавить отдельный endpoint, который отдает HTML-файл нового отчёта (не JSON), с чётко определяемым route и авторизацией, согласованной с текущей схемой внешнего API.
4. Отчёт должен использовать нормализованный `status` из `LogService.STATUS_MAP`, чтобы в UI не было «сырых» числовых кодов для статусов.
5. Фильтрация в отчёте должна опираться на те же поля, которые есть в `Log`/`LogFilter`: `account_id`, `session_id`, `message_id`, `user_id`, `event`, `source`, `status`, `created_at` диапазон.
6. Для non-superuser применять тот же уровень ограничения доступа к данным, который уже применяется в API логов: нельзя раскрывать события чужих пользователей.
7. Предусмотреть возможность открытия отчёта по `account_id`/`number` (в зависимости от выбранного контракта) без изменения старого отчёта.
8. Описать, какие параметры и ограничения доступны в отчёте явно (например, `limit`, сортировка, базовые диапазоны времени), чтобы поведение было воспроизводимым.

### Нефункциональные
1. Соблюсти YAGNI и KISS: в отчёте не дублировать бизнес-логику, только чтение событий и рендеринг.
2. Не изменять текущую модель хранения файлов и не вводить внешние хранилища.
3. Не добавлять синхронный I/O в async-обработчики.
4. Поддержать обратную совместимость: старый endpoint не должен быть удалён или переименован.

## Затронутые файлы (проектная зона реализации)
- **Создать:**
  - `html/account-log-history-report/index.html` — новый статический/шаблонный HTML отчёт по логам (по согласованию с архитектурой шаблона).
  - `html/account-log-history-report/js` и при необходимости `css` для таблицы/фильтров отчёта.
  - `app/api/ext/v1/account_log_report.py` (или расширение `app/api/ext/v1/account_report.py`) — новый endpoint для возврата HTML-страницы.
  - `app/api/ext/v1/__init__.py` — подключение нового роутера.
- **Изменить:**
  - `app/services/log.py` — при необходимости добавить/экспортировать перечисления/справочники, если понадобится расширение фильтрации для отчёта.
  - `app/api/v1/logs.py` — при необходимости добавить недостающие поля/поля сортировки, если их потребуется в UI отчёта.
  - `app/schemas/log.py` — уточнить схему фильтров для отчёта без нарушения обратной совместимости.
- **Дополнительно:** при необходимости обновить внутреннюю документацию в `README.md`/`.opencode/project/*` после согласования.

## Фазы реализации

### Фаза 1. Технический контракт (вопросно-решающий)
- [ ] Подтвердить маршрут и доменную роль нового отчёта: admin-API (JWT) или ext-API (API key).
- [ ] Утвердить источник идентификации для открытия отчёта (`account_id` или `number`) и правила доступа к нему.
- [ ] Утвердить обязательный минимальный набор полей в отчёте (`created_at`, `event`, `source`, `status`, `account_id`, `session_id`, `message_id`, `user_id`, `context`).
- [ ] Зафиксировать требуемые фильтры и пределы пагинации/сортировки (`created_at` window, `event`, `source`, `account_id` и т.д.).

### Фаза 2. Архитектурная интеграция API слоя
- [ ] Определить, где размещается endpoint: отдельный модуль отчётов либо расширение существующего `account_report` для минимальной связанности.
- [ ] Добавить endpoint с `response_class=HTMLResponse` или `FileResponse`, возвращающий html-файл нового отчёта.
- [ ] Включить новый роутер в `app/api/ext/v1/__init__.py` с отдельным tag и префиксом без конфликта старого маршрута.
- [ ] Настроить проверки доступа в соответствии с требованиями и уже существующей моделью зависимости `get_user_by_api_key` / прав пользователей.

### Фаза 3. Проектирование шаблона отчёта и клиента данных
- [ ] Сформировать структуру HTML отчёта для чтения массива событий с возможностью фильтрации и сортировки без сложной бизнес-логики на сервере.
- [ ] Подготовить параметры загрузки данных: единый endpoint логов и трансляцию их в таблицу/таймлайн.
- [ ] Обеспечить отображение `context` и `status` в человекочитаемом виде, используя данные из `LogService` (или явно документируя контракт рендеринга, если использовать сырой JSON).
- [ ] Добавить защиту от перегрузки (`default page size`, `max limit`) либо зафиксировать её в параметрах UI.

### Фаза 4. Безопасность и эксплуатация
- [ ] Проверить, что endpoint не раскрывает данные неавторизованных пользователей и соответствует текущему подходу ограничений в `app/api/v1/logs.py`.
- [ ] Проверить обратную совместимость маршрутов, особенно старого `/ext/api/v1/account/report`.
- [ ] Зафиксировать fallback-логику при пустом/ограниченном наборе логов (например, пустое состояние с понятным сообщением).

## Критерии приёмки
- [ ] Старый отчёт `/ext/api/v1/account/report` продолжает работать как ранее.
- [ ] Новый endpoint доступен по отдельному URL и возвращает корректный `text/html` ответ.
- [ ] Новый отчет показывает события из `Log`, включая все фактически записываемые доменные события.
- [ ] В отчёте отображаются нормализованные статусы (human-friendly), а не сырые числовые коды.
- [ ] Фильтры по `event/source/account_id/created_at` работают детерминированно и воспроизводятся через единые параметры API.
- [ ] Для non-superuser соблюдены ограничения доступа и нет утечки чужих `account_id`/`user_id`.
- [ ] Документация/план согласованы с существующими ограничениями проекта и не требуют изменения существующего роута старого отчёта.

## Риски и вопросы
- Не до конца определено, должен ли новый отчёт принадлежать `admin API` (JWT) или `ext API` (API key), что влияет на модель аутентификации и политику доступа.
- Не до конца определено, должен ли отчёт быть привязан к конкретному `number` (как текущий account report) или к диапазону событий без параметров пути.
- Не определено, какой объём событий по умолчанию нужен для отчёта, иначе есть риск деградации UI на больших выборках.
