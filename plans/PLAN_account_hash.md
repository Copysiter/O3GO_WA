# План: Хранение и обновление hash аккаунта во внешнем API

## Описание

Добавить к аккаунту передаваемое клиентом nullable-поле `hash`, сохранять его при загрузке аккаунта и разрешить его последующее изменение или очистку через два специализированных endpoint внешнего API. Значение должно раскрываться только при атомарной выдаче аккаунта через `GET /ext/api/v1/account/` и не должно попадать в остальные административные, внешние или отчётные ответы.

## Цель

Внешний клиент может сохранить, заменить или очистить `hash` принадлежащего ему аккаунта по `id` либо `number`, а при получении аккаунта для работы получает актуальное значение `hash`. Существующие клиенты, не передающие новое поле, продолжают работать без изменения контрактов ответов.

## Контекст

Сейчас `Account` не содержит `hash`, а схема `AccountExternal` одновременно используется ответом загрузки и ответом выдачи аккаунта. Поэтому добавление поля в общую базовую схему раскроет его через несколько нежелательных API-контрактов, включая вложенные административные ответы. HTML-отчёт аккаунта также динамически выводит все ORM-колонки, поэтому новую колонку необходимо явно исключить из отчёта.

## Требования

### Функциональные требования

1. `POST /ext/api/v1/account/upload` принимает необязательное multipart-поле `hash` и сохраняет переданное значение при создании аккаунта; алгоритм, формат и уникальность значения сервером не проверяются.
2. При повторной загрузке существующего аккаунта явно переданный непустой `hash` заменяет текущее значение, а отсутствие multipart-поля сохраняет прежний `hash`; очистка выполняется специализированными JSON-endpoint.
3. `POST /ext/api/v1/account/{id}/hash` принимает JSON `{"hash": <string|null>}` и устанавливает либо очищает `hash` аккаунта с указанным `id`.
4. `POST /ext/api/v1/account/hash` принимает JSON с обязательным `hash` и ровно одним идентификатором: `{"id": <int>, "hash": <string|null>}` либо `{"number": <string>, "hash": <string|null>}`. Одновременное присутствие или отсутствие `id` и `number` отклоняется как `422 Unprocessable Entity`.
5. Оба endpoint обновления требуют действующий API Key, изменяют только аккаунт его владельца и возвращают `404 Not Found` как для отсутствующего, так и для чужого аккаунта, чтобы не раскрывать существование чужих записей.
6. Поскольку `number` не уникален на уровне БД, поиск по номеру выполняется в пределах владельца; отсутствие совпадений возвращает `404 Not Found`, а несколько совпадений — `409 Conflict` без произвольного выбора записи.
7. Успешное специализированное обновление, включая очистку через `null`, принудительно переводит аккаунт в `AVAILABLE` и возвращает `200 OK` с полями `id`, `number`, `hash`, `status`.
8. Только `GET /ext/api/v1/account/` возвращает `hash`; `POST /ext/api/v1/account/upload`, административные Account API, вложенные Account-представления, Android/Session API и HTML-отчёт его не возвращают.
9. Изменение `hash` фиксируется аудит-событием `account.update` с `source=ext_api`, идентификаторами аккаунта и пользователя, но само значение `hash` не записывается в аудит или application logs.
10. `GET /ext/api/v1/account/` рассматривает аккаунт как доступный по данным подключения, если заполнено хотя бы одно из полей: `file_name` или `hash`.

### Нефункциональные требования

1. Колонка `hash` является nullable, не имеет unique constraint и индекса, чтобы поддержать существующие записи и согласованную пользователем неуникальность.
2. Значение хранится как непрозрачная строка без серверного вычисления и зависимости от конкретного hash-алгоритма.
3. Специализированное изменение `hash` не должно менять `status`, `cooldown`, владельца и операционный `updated_at`, используемый при выборе и cooldown аккаунта.
4. Добавление входного поля загрузки и отдельного поля ответа должно сохранять обратную совместимость внешнего API.
5. Запись `hash` и аудит-события выполняются в одной транзакции с явным commit по действующим конвенциям проекта.

## Технические детали реализации

Поле следует добавить непосредственно в ORM-модель как nullable `String` без ограничения уникальности и индекса. Входные и выходные схемы необходимо разделить: `hash` добавляется в `AccountUpload`, создаются две специализированные схемы изменения и отдельная response schema выдачи аккаунта, наследующая текущий внешний контракт и добавляющая только `hash`; общие `AccountBase` и `AccountExternal` остаются без этого поля. Оба POST-endpoint используют общую операцию поиска, проверки владельца, обновления и аудита, чтобы их поведение не расходилось. Для обновления по `number` репозиторий должен обнаруживать неоднозначность, а специализированная запись должна сохранять прежний `updated_at`, поскольку это поле участвует в cooldown и порядке выдачи аккаунтов.

## Scope изменений

**Создать:**

- `migrations/versions/<revision>_add_hash_to_account.py` — обратимая миграция nullable-колонки `account.hash` без индекса и unique constraint.
- `tests/api/ext/v1/test_account_hash.py` — контрактные и интеграционные проверки загрузки, изменения, очистки, ownership и контролируемого раскрытия `hash`.

**Изменить:**

- `app/models/account.py` — ORM-поле `hash`.
- `app/schemas/account.py` — входное поле загрузки, две схемы специализированного обновления и отдельная схема ответа выдачи аккаунта.
- `app/schemas/__init__.py` — экспорт новых Account-схем.
- `app/crud/account.py` — детерминированный поиск аккаунта владельца и специализированное обновление `hash` без изменения операционного `updated_at`.
- `app/api/ext/v1/account.py` — сохранение `hash` при загрузке, два POST-endpoint, единая проверка ownership и использование отдельной response schema только для `GET /ext/api/v1/account/`.
- `app/api/ext/v1/account_report.py` — явное исключение `hash` из динамического списка колонок HTML-отчёта.

**Удалить:**

- Файлы не удаляются.

## Фазы реализации

### Фаза 1: Персистентность и изолированные контракты

- [x] Добавить nullable-поле `hash` в ORM-модель без default, индекса и unique constraint.
- [x] Создать Alembic-миграцию от актуального head с `upgrade()` для добавления и `downgrade()` для удаления колонки.
- [x] Добавить необязательный `hash` во входную multipart-схему загрузки, не добавляя его в `AccountBase`, `AccountExternal`, административные и отчётные схемы.
- [x] Создать schema для изменения по path-id, schema с взаимоисключающими `id`/`number` для body-поиска и отдельную output schema выдачи аккаунта с `hash`.

### Фаза 2: Операции поиска и обновления

- [x] Добавить в Account repository поиск по `id + user_id` и детерминированный поиск по `number + user_id`, способный различить ноль, одно и несколько совпадений.
- [x] Добавить единую операцию записи nullable `hash`, которая не меняет операционный `updated_at` и не затрагивает другие поля аккаунта.
- [x] Сохранить входной `hash` в create-ветке загрузки и обновлять его в update-ветке только при явной передаче значения; при отсутствии поля оставить прежнее значение.
- [x] Не включать значение `hash` в структурированные application logs и контекст аудит-события.

### Фаза 3: Специализированные endpoint и выдача

- [x] Реализовать `POST /ext/api/v1/account/{id}/hash` с JSON-телом изменения, ownership-проверкой, атомарным аудитом и ответом `204 No Content`.
- [x] Реализовать `POST /ext/api/v1/account/hash` с выбором ровно одного locator, обработкой `404` и неоднозначного номера через `409`, атомарным аудитом и ответом `204 No Content`.
- [x] Переключить только `GET /ext/api/v1/account/` на специализированную response schema, включающую nullable `hash`; сохранить response model загрузки без `hash`.
- [x] Исключить `hash` из динамически сформированного HTML-отчёта аккаунта и проверить отсутствие поля во всех остальных Account responses.

### Фаза 4: Проверка поведения и совместимости

- [x] Покрыть создание аккаунта с `hash`, создание без него, повторную загрузку с заменой и повторную загрузку без изменения существующего значения.
- [x] Покрыть изменение и очистку по path-id, body-id и body-number, включая `422`, `404` и `409`.
- [x] Проверить запрет изменения чужого аккаунта и отсутствие различимого ответа между чужой и несуществующей записью.
- [x] Проверить, что `hash` присутствует только в ответе выдачи, отсутствует в ответе загрузки, административных схемах и HTML-отчёте, а значение не попадает в logs/audit.
- [x] Проверить migration upgrade/downgrade на таблице с существующими аккаунтами и неизменность `updated_at`, статуса и cooldown при специализированном обновлении.

### Фаза 5: Обновлённый контракт статуса и выдачи

- [x] Обновлять `hash` и принудительно устанавливать `AccountStatus.AVAILABLE` одной операцией без изменения `updated_at`.
- [x] Заменить обязательность архива в `GET /ext/api/v1/account/` условием `file_name IS NOT NULL OR hash IS NOT NULL`.
- [x] Обновить контрактные и регрессионные тесты для нового ответа, статуса и условия выдачи.

## Критерии приёмки

- [x] Аккаунт, загруженный с `hash`, сохраняет переданное значение, а старый клиент без нового multipart-поля продолжает успешно загружать аккаунт.
- [x] Оба POST-endpoint устанавливают новое значение, очищают его через явный `null`, переводят аккаунт в `AVAILABLE` и возвращают `200 OK` с `id`, `number`, `hash`, `status`.
- [x] Body-endpoint принимает ровно один из `id` и `number`; невалидный locator возвращает `422`, неоднозначный номер — `409`.
- [x] API Key не позволяет изменить чужой аккаунт, и такой запрос возвращает тот же `404`, что и запрос к отсутствующему аккаунту.
- [x] `GET /ext/api/v1/account/` возвращает актуальный nullable `hash`, а остальные API-ответы и HTML-отчёт поле не раскрывают.
- [x] Значение `hash` не имеет unique constraint, может совпадать у разных аккаунтов и может быть `NULL` у существующих записей.
- [x] Специализированное обновление не меняет `updated_at`, `cooldown` и остальные данные аккаунта, кроме принудительной установки статуса `AVAILABLE`; аудит записывается атомарно без самого значения `hash`.
- [x] `GET /ext/api/v1/account/` допускает выдачу аккаунта с отсутствующим `file_name`, если его `hash` не равен `NULL`, и исключает аккаунты, у которых оба поля равны `NULL`.
- [x] Миграция содержит рабочие `upgrade()` и `downgrade()` и применима к БД с существующими аккаунтами.

## Риски

| Риск | Влияние | Смягчение |
|------|---------|-----------|
| Общая `AccountExternal` используется несколькими endpoint и при прямом расширении раскроет `hash` в ответе загрузки | Высокое | Использовать отдельную response schema только для атомарной выдачи аккаунта |
| `number` не уникален и generic `get_by` способен молча выбрать произвольную запись | Высокое | Ограничить поиск владельцем и возвращать `409` при нескольких совпадениях |
| ORM `onupdate` для `updated_at` может изменить cooldown и порядок выдачи после смены метаданных | Высокое | Реализовать специализированное обновление с явным сохранением прежнего `updated_at` и регрессионным тестом |
| HTML-отчёт автоматически выводит новые ORM-колонки | Среднее | Явно исключить `hash` из списка колонок отчёта и проверить отсутствие в тесте |
| Историческая Alembic-цепочка содержит повторное добавление `attempts` и может мешать fresh upgrade независимо от этой задачи | Среднее | Строить новую ревизию от фактического head, проверить целевую БД; исправление старой цепочки вынести в отдельную задачу |

## Зависимости

- Клиент внешнего API передаёт уже вычисленное значение `hash`; сервер не выбирает и не реализует hash-алгоритм.
- Аутентификация и область владения используют существующую зависимость `get_user_by_api_key` и `Account.user_id`.
- Реализация зависит от подтверждения фактического Alembic head в среде развёртывания из-за известной проблемы исторических ревизий.

## Заметки

Блокирующих нерешённых вопросов по API-контракту нет. Поле намеренно не добавляется в административный `PUT /api/v1/accounts/{id}` и общие Account-схемы; это предотвращает как изменение через административный API, так и случайное раскрытие во вложенных ответах.
