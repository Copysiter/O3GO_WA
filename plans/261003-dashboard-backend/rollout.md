# Stats: операторский чек-лист включения и отката

**Дата:** 2026-10-05. **Статус:** подготовлен, не выполнен.

Пользователь одобрил локальную приёмку фазы 5 и подготовку безопасного включения. Production rollout не выполнялся. Результаты проверок, их итоговые количества и закрытие пунктов ведёт основной исполнитель в [plan.md](plan.md); этот документ не подтверждает выполнение открытых операционных пунктов фаз 2–3.

## 1. Недостающие входные данные оператора

- [ ] Предоставить явно разрешённый read-only endpoint рабочей БД либо обезличенный операторский отчёт: версия PostgreSQL, фактическая схема `user/account/session/message/log`, колонки и ограничения/FK, существующие индексы, применённые ревизии Alembic и соответствие выбранному релизу. Приложить оценки числа строк и размеров таблиц/индексов, объёма истории, политики retention, удалений и известных пропусков аудита.
- [ ] Подтвердить открытые семантические решения плана: аналитика сохранившихся данных с текущим владельцем и включение административных статусов сообщений в подтверждения. Каскадное удаление истории предусмотрено моделью `app/models/log.py`; полноту истории нельзя вывести из наличия старой строки.
- [ ] Предоставить подтверждение rollout аудита `session.error` на **всех** обслуживающих start/finish/ban workers и решение по каждой из четырёх групп coverage: подтверждённое начало непрерывного доступного учёта в UTC с основанием либо явно неизвестный охват. Даты реализации и `MIN(log.created_at)` не заменяют эти сведения.
- [ ] Согласовать репрезентативный объём и распределение данных, глубину сохранённой истории, области member/admin-selected/admin-all, периоды и конкурентность запросов. Задать численные критерии задержки, стоимости SQL/нагрузки на БД, длительность наблюдения и пороги остановки; учесть live каждые 60 секунд на открытый дашборд. Локальные синтетические замеры не задают production SLA.
- [ ] Выбрать проверенный релизный артефакт backend и статических файлов, версию конфигурации, предыдущий проверенный комплект для отката, ответственного и окно работ. Указать фактические экземпляры/workers, адреса и порты UI/API, маршрутизацию и согласованный способ закрыть/открыть реальные stats UI/API на всех путях доступа, включая прямой API-порт. Рабочее дерево при подготовке содержит незакоммиченные изменения; один текущий `HEAD` не идентифицирует проверенный комплект. Автоматические commit, сборка и deployment не предусмотрены.

Для отчёта metadata достаточно ограниченного чтения каталогов по перечисленным таблицам: `information_schema.columns`, `pg_constraint`, `pg_indexes`, оценок `pg_class`/`pg_stat_user_tables` и таблицы ревизий Alembic. Использовать отдельную read-only-сессию с согласованными лимитами времени и объёма вывода. Полные сканирования журнала, `EXPLAIN ANALYZE`, `ANALYZE` и DDL рабочей БД не являются частью этой проверки. Retention и начало полноты учёта подтверждает оператор.

## 2. Фактические особенности запуска

| Основание в исходниках | Что проверить оператору до запуска, включая откат |
|---|---|
| `app/lifespan.py` вызывает `init_db()`. В `app/adapters/db/init_db.py` выполняются `drop_all` при `DATABASE_DELETE_ALL=True` и `create_all` при `DATABASE_CREATE_ALL=True`. Defaults в `app/core/settings/database_settings.py`: соответственно **False** и **True**. | Подтвердить эффективные **False для обоих** флагов. Запуск приложения не подходит для read-only проверки metadata. Затем `create_superuser()` всё равно проверяет пользователя `FIRST_SUPERUSER` и при отсутствии создаёт его; подтвердить ожидаемое состояние без выгрузки credentials. |
| Lifespan безусловно запускает scheduler. `app/main.py` передаёт `ASGI_WORKERS` в Uvicorn; default равен **1**. `app/jobs/scheduler.py` задаёт `max_instances=1` внутри одного scheduler. Jobs в `app/jobs/hourly/` изменяют данные с commit на 0-й и 5-й минутах каждого часа UTC. | При нескольких workers/экземплярах запускаются несколько планировщиков; локальный `max_instances` не исключает межпроцессное дублирование запусков. Подтвердить топологию и порядок замены, включая временное перекрытие старых и новых экземпляров. Флага отключения jobs в прочитанных settings нет. |
| `app/main.py` объединяет административное и внешнее API; `app/api/v1/__init__.py` регистрирует stats без условия. `STATS_COVERAGE_STARTS={}` по умолчанию описывает неизвестный охват. | Аудит и stats поставляются в одном backend. Coverage не выключает маршруты или аналитические SELECT; отдельного stats feature flag нет. Порядок открытия доступа ниже требует заранее выбранного операторского механизма, а не отдельного бинарного файла или придуманного переключателя. |
| `docker-compose.yml`: `api` собирается через корневой `Dockerfile`, `./app` и `./html` подключены как bind mounts; указан `env_file`. `services/nginx.conf` обслуживает статику и не содержит действующего API proxy. `html/static/auth.js` выбирает `api_base_url` по адресу страницы. | Зафиксировать реально используемые конфигурационные файлы и содержимое подключаемых каталогов: тег образа не гарантирует версию bind mounts. Сверить адрес API, CORS и порты: Compose направляет API на порт 8000 контейнера, тогда как default `PROJECT_PORT` — 8080. Эти файлы не подтверждают production-топологию. |

`app/core/settings/general_settings.py` объединяет пять групп settings, объявляет чтение `.env` и создаёт объект при импорте. Рабочая `.env` при подготовке не читалась; эффективные безопасные значения подтверждает оператор без вывода секретов. Применение coverage-конфигурации ко всем workers должно учитывать повторные startup-действия.

## 3. Последовательность включения

- [ ] **Подтвердить приёмку.** Получить завершённые результаты основного исполнителя из [plan.md](plan.md), закрыть проверку metadata и согласовать стоимость на репрезентативном изолированном наборе. Snapshot-проверка в `tests/integration/test_stats_concurrency.py` оборачивает фактический service SELECT тестовым advisory gate: проверяет один snapshot через конкурентный commit, но не порядок выполнения CTE и не нагрузочный SLA. Этот gate применяется только в тестовой БД.
- [ ] **Подготовить ограничение доступа.** Проверить выбранный операторский механизм закрытия реального `/dashboard/` и `/api/v1/stats/*`, включая запросы уже открытых страниц и обходные пути к API. Пока механизм и rollback baseline не определены, совместный backend нельзя считать независимо поэтапно включаемым. Скрытия ссылки в меню недостаточно.
- [ ] **Сначала ввести аудит.** По согласованной процедуре оператора развернуть выбранный backend с `SessionErrorAudit`, сохраняя ограничение stats. Подтвердить версии всех обслуживающих workers, завершение замены старых, работу независимого сохранения `session.error` и отсутствие отказов аудита по разрешённым пробам/наблюдениям. Зафиксировать фактическое время UTC; готовность кода и успешный старт одного worker недостаточны.
- [ ] **Затем подтвердить coverage.** Для каждой группы оформить основание, время UTC и подтверждающего оператора:
  - `lifecycle` — начало и сохранность нужных событий сессий/аккаунтов, включая scheduler;
  - `message_events` — начало и сохранность зарегистрированных подтверждений сообщений;
  - `account_errors` — учёт ошибок операций аккаунтов с `operation_id`;
  - `session_errors` — учёт ошибок start/finish/ban с `operation_id` после фактического rollout всех workers.

  В `STATS_COVERAGE_STARTS` включать только подтверждённые группы со строгими RFC 3339 timestamps в UTC. Неизвестную группу оставлять отсутствующей; `{}` допустим, явный JSON `null` и null-значения недопустимы. Не выводить начало учёта из текущей даты или первой записи журнала. Проверить одинаковую конфигурацию на всех workers; настройка не восстанавливает пропущенные события.
- [ ] **После аудита и решения по coverage открыть чтение.** Сначала разрешить ограниченные smoke-пробы read-API, затем доступ к реальному frontend с согласованным backend/static комплектом, включая `html/static/auth.js` и `script.js`. Выполнить проверки ниже и наблюдать согласованные задержки, SQL-стоимость, ошибки аудита и число scheduler-процессов. При превышении порогов перейти к откату. Отдельные команды deployment определяет оператор для подтверждённого окружения.

## 4. Smoke-проверки

Выполнять короткие согласованные GET-пробы на разрешённых учётных записях и периодах; результаты фиксировать без тел запросов/ответов и credentials.

- [ ] **Member:** `GET /api/v1/stats/summary` с корректным прошлым UTC-периодом и `GET /api/v1/stats/live` возвращают 200 и собственный scope. Чужой существующий и несуществующий `user_id` дают одинаковый 403. `GET /api/v1/options/user` возвращает только себя и поля `text/value`, в том числе при подставленных клиентских параметрах.
- [ ] **Admin:** оба stats GET без `user_id` дают общую область, с выбранным владельцем — только его данные; несуществующий владелец даёт 404. Options содержат публичные `text/value`, включая неактивных владельцев. Проверить отсутствие приватного контекста и секретных полей, не сохраняя их значения в отчёте.
- [ ] **Авторизация:** stats/options без JWT дают 401, с невалидным JWT — 403, для неактивного пользователя — 400. DashboardApi и общий auth poll используют свежий `Authorization: Bearer …`; после смены входа старый ответ не меняет текущую сессию, logout очищает вход. Имя в header отображается как текст. Результаты локальных race/header-регрессий сверить с основным планом.
- [ ] **Coverage:** на непустом диапазоне без подтверждённого охвата соответствующие событийные счётчики равны `null`, присутствует причина, UI показывает «—», сравнение с неизвестным previous не вычисляется. `message_created`, cohort и live не обязаны быть `null`. При частичном охвате полностью покрытые buckets сохраняют числа; пустой диапазон даёт нули и пустой ряд.
- [ ] **Период и live:** проверить UTC, открытый конец через отсутствие `end_at`, равные границы и 422 для некорректного диапазона. Live не принимает период, обновляется независимо от ошибки summary/невалидных дат и после смены владельца не показывает прежнюю область; таймер — 60 секунд. Полную календарную матрицу и сверку totals/buckets брать из локальной приёмки основного исполнителя.
- [ ] **Источник и ошибки:** обычный `/dashboard/` читает API; при отказе отображает ошибку/недоступность, а не вымышленные данные или ложные нули. Mock допустим только при явном `?demo=1` и не является fallback. Искусственные отказы БД/аудита проверяются изолированно, а не создаются на рабочем сервисе ради smoke.

## 5. Откат

- [ ] При нарушении области доступа, недостоверном coverage, регрессии auth/основных операций или превышении согласованных порогов явно закрыть **реальные stats UI и API** выбранным операторским механизмом. Проверить прекращение чтения и через прямые API-пути, и из ранее открытого UI. Встроенного feature flag нет; перевод на mock и одно лишь скрытие меню не являются откатом.
- [ ] Восстановить предыдущий проверенный комплект backend, статических файлов и конфигурации, включая версии bind mounts. Повторно проверить startup-флаги и топологию scheduler, базовую авторизацию и прежние функции по принятой процедуре оператора. Миграции, downgrade схемы, новые индексы, удаление истории и backfill не выполняются.
- [ ] Если откат остановил producer либо обнаружен разрыв учёта, снять подтверждение затронутого coverage. При следующем включении оставить соответствующие группы отсутствующими до подтверждения нового непрерывного интервала; прежняя дата не должна скрывать разрыв. Сохранённый аудит не переписывать.
- [ ] Зафиксировать время ограничения доступа и восстановления в UTC, причину, версии до/после, результаты контрольных проб и решение о дальнейшей доступности stats. Повторное открытие требует устранения причины и повторной приёмки затронутых проверок.

## 6. Свидетельства и незакрытые условия

- [ ] В журнале выполнения сохранить UTC-время, оператора, идентификаторы артефактов/конфигураций, охват экземпляров, источник metadata и основание каждой coverage-даты. Для проб достаточно роли/области, маршрута, границ периода, HTTP-кода, задержки, результата проверки и ссылки на обезличенный отчёт.
- [ ] Не включать API keys, JWT/Authorization, пароли, DSN с credentials, payload аккаунтов/сообщений и полные HTTP/аудит-контексты. Незавершённые проверки не помечать успешными; итог и закрытие операционных пунктов передать основному исполнителю для [plan.md](plan.md).

**Открыто на момент подготовки:** рабочие metadata/retention, подтверждённый rollout аудита и coverage по группам, репрезентативный объём и численные критерии стоимости, выбранный релиз/конфигурация/rollback baseline и механизм ограничения реальных stats UI/API. Подготовленный чек-лист эти условия не закрывает.
