# Stats: операторский чек-лист включения и отката

**Дата:** 2026-10-05. **Статус:** подготовлен, не выполнен.

Пользователь одобрил локальную приёмку фазы 5, а затем прямо поручил унифицировать аудит upload/start/finish/ban в LogService и считать сохранённую историю без ручных дат начала сбора. Чек-лист обновлён под этот код; прежнее условие подтверждения coverage-дат отменено. Production rollout не выполнялся. Результаты проверок, их итоговые количества и закрытие пунктов ведёт основной исполнитель в [plan.md](plan.md).

Текущий контракт считает сохранившиеся данные: lifecycle, сообщения и live используют текущего владельца аккаунта, error-группы — вызывающего пользователя в `log.user_id` и группировку по event/user/operation_id. Зарегистрированные административные статусы сообщений входят в подтверждения. Каскадное удаление истории предусмотрено моделью `app/models/log.py`. Число и состояние `recorded` означают возможность подсчёта сохранённых записей, а не полноту сбора; ноль означает отсутствие записанных событий. Четыре wire-группы `coverage` сохранены с `from: null`, без конфигурации начала сбора и без фиктивных дат.

## 1. Недостающие входные данные оператора

- [ ] Предоставить явно разрешённый read-only endpoint рабочей БД либо обезличенный операторский отчёт: версия PostgreSQL, фактическая схема `user/account/session/message/log`, колонки и ограничения/FK, существующие индексы, применённые ревизии Alembic и соответствие выбранному релизу. Приложить оценки числа строк и размеров таблиц/индексов, объёма истории, политики retention, удалений и известных пропусков аудита.
- [ ] Указать **все** обслуживающие upload/start/finish/ban workers для проверки версии и работы общего LogService-аудита после релиза: `account.error` для upload и `session.error` для start/finish/ban. Подтверждение работы независимого writer остаётся операционным пунктом; даты начала непрерывного сбора для групп не требуются.
- [ ] Согласовать репрезентативный объём и распределение данных, глубину сохранённой истории, области member/admin-selected/admin-all, периоды и конкурентность запросов. Задать численные критерии задержки, стоимости SQL/нагрузки на БД, длительность наблюдения и пороги остановки; учесть live каждые 60 секунд на открытый дашборд. Локальные синтетические замеры не задают production SLA.
- [ ] Выбрать проверенный релизный артефакт backend и статических файлов, версию конфигурации, предыдущий проверенный комплект для отката, ответственного и окно работ. Указать фактические экземпляры/workers, адреса и порты UI/API, маршрутизацию и согласованный способ закрыть/открыть реальные stats UI/API на всех путях доступа, включая прямой API-порт. Рабочее дерево при подготовке содержит незакоммиченные изменения; один текущий `HEAD` не идентифицирует проверенный комплект. Автоматические commit, сборка и deployment не предусмотрены.

Для отчёта metadata достаточно ограниченного чтения каталогов по перечисленным таблицам: `information_schema.columns`, `pg_constraint`, `pg_indexes`, оценок `pg_class`/`pg_stat_user_tables` и таблицы ревизий Alembic. Использовать отдельную read-only-сессию с согласованными лимитами времени и объёма вывода. Полные сканирования журнала, `EXPLAIN ANALYZE`, `ANALYZE` и DDL рабочей БД не являются частью этой проверки. Оператор описывает retention и известные пропуски; эти сведения не превращаются в дату, управляющую численными метриками.

## 2. Фактические особенности запуска

| Основание в исходниках | Что проверить оператору до запуска, включая откат |
|---|---|
| `app/lifespan.py` вызывает `init_db()`. В `app/adapters/db/init_db.py` выполняются `drop_all` при `DATABASE_DELETE_ALL=True` и `create_all` при `DATABASE_CREATE_ALL=True`. Defaults в `app/core/settings/database_settings.py`: соответственно **False** и **True**. | Подтвердить эффективные **False для обоих** флагов. Запуск приложения не подходит для read-only проверки metadata. Затем `create_superuser()` всё равно проверяет пользователя `FIRST_SUPERUSER` и при отсутствии создаёт его; подтвердить ожидаемое состояние без выгрузки credentials. |
| Lifespan безусловно запускает scheduler. `app/main.py` передаёт `ASGI_WORKERS` в Uvicorn; default равен **1**. `app/jobs/scheduler.py` задаёт `max_instances=1` внутри одного scheduler. Jobs в `app/jobs/hourly/` изменяют данные с commit на 0-й и 5-й минутах каждого часа UTC. | При нескольких workers/экземплярах запускаются несколько планировщиков; локальный `max_instances` не исключает межпроцессное дублирование запусков. Подтвердить топологию и порядок замены, включая временное перекрытие старых и новых экземпляров. Флага отключения jobs в прочитанных settings нет. |
| `app/main.py` объединяет административное и внешнее API; `app/api/v1/__init__.py` регистрирует stats без условия. Метрики сохранённой истории доступны без настройки начала сбора. | Общий LogService-аудит и stats поставляются в одном backend; отдельного stats feature flag нет. Порядок открытия доступа ниже использует заранее выбранный операторский механизм. Скрытая пользователем ссылка меню через `dashboardNavigation1=''` не закрывает прямой `/dashboard/` и stats API. |
| `docker-compose.yml`: `api` собирается через корневой `Dockerfile`, `./app` и `./html` подключены как bind mounts; указан `env_file`. `services/nginx.conf` обслуживает статику и не содержит действующего API proxy. `html/static/auth.js` выбирает `api_base_url` по адресу страницы. | Зафиксировать реально используемые конфигурационные файлы и содержимое подключаемых каталогов: тег образа не гарантирует версию bind mounts. Сверить адрес API, CORS и порты: Compose направляет API на порт 8000 контейнера, тогда как default `PROJECT_PORT` — 8080. Эти файлы не подтверждают production-топологию. |

`app/core/settings/general_settings.py` объединяет пять групп settings, объявляет чтение `.env` и создаёт объект при импорте. Рабочая `.env` при подготовке не читалась; эффективные безопасные значения подтверждает оператор без вывода секретов. Замена версии backend на всех workers должна учитывать повторные startup-действия. Пользовательское изменение публикации БД на порт 5433 в `docker-compose.yml` не относится к унификации и не подтверждает production-топологию.

## 3. Последовательность включения

- [ ] **Подтвердить приёмку.** Получить завершённые результаты основного исполнителя из [plan.md](plan.md), закрыть проверку metadata и согласовать стоимость на репрезентативном изолированном наборе. Snapshot-проверка в `tests/integration/test_stats_concurrency.py` оборачивает фактический service SELECT тестовым advisory gate: проверяет один snapshot через конкурентный commit, но не порядок выполнения CTE и не нагрузочный SLA. Этот gate применяется только в тестовой БД.
- [ ] **Подготовить ограничение доступа.** Проверить выбранный операторский механизм закрытия реального `/dashboard/` и `/api/v1/stats/*`, включая запросы уже открытых страниц и обходные пути к API. Пока механизм и rollback baseline не определены, совместный backend нельзя считать независимо поэтапно включаемым. Скрытия ссылки в меню недостаточно.
- [ ] **Ввести общий аудит.** По согласованной процедуре оператора развернуть выбранный backend с `LogService` из `app/services/log.py`, сохраняя ограничение stats. Подтвердить версии всех обслуживающих upload/start/finish/ban workers, завершение замены старых, независимое сохранение `account.error`/`session.error` и отсутствие отказов аудита по разрешённым пробам/наблюдениям. В журнале релиза зафиксировать время UTC и охват экземпляров; это сведения о deployment, а не начало гарантированно полного сбора.
- [ ] **Проверить контракт аудита.** Сверить с результатами изолированной приёмки: `LogOperation` содержит только состояние запроса, `report_error` подтверждает освобождение бизнес-транзакции до `record_independent`, bool означает освобождение, при неподтверждённом освобождении новые writers блокируются. Ошибки одного запроса имеют общий operation UUID и корректного вызывающего пользователя; новые FK допустимы только после подтверждённого commit. Обычные post-commit ошибки cleanup/success logger upload сохраняют HTTP 201. Защищённое завершение и обязательный минимальный stderr fallback, включая неожиданный отказ finalizer/защищённой задачи, проверяются изолированно; на рабочем сервисе наблюдаются штатные диагностические каналы.
- [ ] **Открыть чтение сохранённой истории.** Сначала разрешить ограниченные smoke-пробы read-API, затем доступ к реальному frontend с согласованным backend/static комплектом, включая `html/static/auth.js` и `script.js`. Выполнить проверки ниже и наблюдать согласованные задержки, SQL-стоимость, ошибки аудита и число scheduler-процессов. При превышении порогов перейти к откату. Отдельные команды deployment определяет оператор для подтверждённого окружения; ручная конфигурация coverage-дат в этой последовательности отсутствует.

## 4. Smoke-проверки

Выполнять короткие согласованные GET-пробы на разрешённых учётных записях и периодах; результаты фиксировать без тел запросов/ответов и credentials.

- [ ] **Member:** `GET /api/v1/stats/summary` с корректным прошлым UTC-периодом и `GET /api/v1/stats/live` возвращают 200 и собственный scope. Чужой существующий и несуществующий `user_id` дают одинаковый 403. `GET /api/v1/options/user` возвращает только себя и поля `text/value`, в том числе при подставленных клиентских параметрах.
- [ ] **Admin:** оба stats GET без `user_id` дают общую область, с выбранным владельцем — только его данные; несуществующий владелец даёт 404. Options содержат публичные `text/value`, включая неактивных владельцев. Проверить отсутствие приватного контекста и секретных полей, не сохраняя их значения в отчёте.
- [ ] **Авторизация:** stats/options без JWT дают 401, с невалидным JWT — 403, для неактивного пользователя — 400. DashboardApi и общий auth poll используют свежий `Authorization: Bearer …`; после смены входа старый ответ не меняет текущую сессию, logout очищает вход. Имя в header отображается как текст. Результаты локальных race/header-регрессий сверить с основным планом.
- [ ] **Сохранённая история:** summary содержит четыре группы `lifecycle/message_events/account_errors/session_errors`, все с `from: null`. При отсутствии записанных событий счётчики равны нулю и состояние — `recorded`; отсутствие подтверждённой даты сбора не вызывает NULL. UI поясняет семантику сохранённой истории и нулей, не показывает legacy `coverage.from` как гарантированное начало сбора. Пустой диапазон даёт нули и пустой ряд.
- [ ] **Качество error-групп:** единственная текущая причина `partial` — `missing_operation_id`. При наличии таких сохранённых строк вся соответствующая error-группа затронутого current/previous периода маскируется в `null`, включая все buckets этого периода; остальные группы, cohort и live сохраняют свой контракт. UI показывает предупреждение и «—», сравнение с неизвестным previous не вычисляется. Сценарий проверяется по имеющимся разрешённым данным либо результатам изолированных fixtures; создавать дефектную историю в рабочей БД для smoke не требуется.
- [ ] **Период и live:** проверить UTC, открытый конец через отсутствие `end_at`, равные границы и 422 для некорректного диапазона. Live не принимает период, обновляется независимо от ошибки summary/невалидных дат и после смены владельца не показывает прежнюю область; таймер — 60 секунд. Полную календарную матрицу и сверку totals/buckets брать из локальной приёмки основного исполнителя.
- [ ] **Источник и ошибки:** обычный прямой `/dashboard/` читает API при сохранённой скрытой ссылке общего меню; при отказе отображает ошибку/недоступность, а не вымышленные данные или ложные нули. Mock допустим только при явном `?demo=1` и не является fallback. Искусственные отказы БД/аудита проверяются изолированно, а не создаются на рабочем сервисе ради smoke.

## 5. Откат

- [ ] При нарушении области доступа, неверных агрегатах/маскировании error-групп, отказах аудита, регрессии auth/основных операций или превышении согласованных порогов явно закрыть **реальные stats UI и API** выбранным операторским механизмом. Проверить прекращение чтения и через прямые API-пути, и из ранее открытого UI. Встроенного feature flag нет; перевод на mock и одно лишь скрытие меню не являются откатом.
- [ ] Восстановить предыдущий проверенный комплект backend, статических файлов и конфигурации, включая версии bind mounts. Повторно проверить startup-флаги и топологию scheduler, базовую авторизацию и прежние функции по принятой процедуре оператора. Миграции, downgrade схемы, новые индексы, удаление истории и backfill не выполняются.
- [ ] Если откат остановил producer либо обнаружен разрыв учёта, зафиксировать затронутые операции/workers и известный пропуск в журнале эксплуатации. Сохранённый аудит не переписывать и не восстанавливать вымышленными событиями. При следующем включении подтвердить работу общего аудита и корректность подсчёта сохранённых записей; `recorded` по-прежнему не гарантирует полноту истории и не исключает пропуски.
- [ ] Зафиксировать время ограничения доступа и восстановления в UTC, причину, версии до/после, результаты контрольных проб и решение о дальнейшей доступности stats. Повторное открытие требует устранения причины и повторной приёмки затронутых проверок.

## 6. Свидетельства и незакрытые условия

- [ ] В журнале выполнения сохранить UTC-время операций релиза/отката, оператора, идентификаторы артефактов/конфигураций, охват экземпляров, подтверждение работы аудита, источник metadata и известные ограничения retention. Для проб достаточно роли/области, маршрута, границ периода, HTTP-кода, задержки, результата проверки и ссылки на обезличенный отчёт.
- [ ] Не включать API keys, JWT/Authorization, пароли, DSN с credentials, payload аккаунтов/сообщений и полные HTTP/аудит-контексты. Незавершённые проверки не помечать успешными; итог и закрытие операционных пунктов передать основному исполнителю для [plan.md](plan.md).

**Открыто на момент подготовки:** рабочие metadata/retention, подтверждение общего аудита upload/start/finish/ban на всех обслуживающих workers, репрезентативный объём и численные критерии стоимости, выбранный релиз/конфигурация/rollback baseline и механизм ограничения реальных stats UI/API. Подготовленный чек-лист эти условия не закрывает. Ручные даты начала сбора исключены из условий включения прямым поручением пользователя.
