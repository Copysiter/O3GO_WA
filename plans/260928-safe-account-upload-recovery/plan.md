# Безопасная загрузка и восстановление архивов аккаунтов

## Описание

Изменить только бизнес-логику `POST /ext/api/v1/account/upload`: сохранять новый архив до изменения БД, проверять результат `UPDATE ... RETURNING` и удалять прежние файлы только после успешного commit. Ошибки операции записывать отдельной транзакцией как `account.error`, разрешив отсутствие ссылки на ещё не созданный аккаунт. Добавить самостоятельный скрипт `app/restore_missing_files.py`, который заменяет отсутствующую файловую ссылку на свободную альтернативу с максимальным timestamp в имени.

## Цель

Сбой upload до подтверждённого commit не удаляет ранее существовавшие старые файлы, а при доступной БД диагностическое событие сохраняется независимо от rollback основной операции. Восстановление назначает существующий, не используемый другими аккаунтами архив по согласованному правилу и не изменяет остальные поля аккаунта или содержимое файлов.

## Контекст

Сейчас ветка обновления upload удаляет прежние файлы до записи новых и фиксации изменений, а в словарь UPDATE безусловно попадает `type=None` при отсутствии соответствующего параметра. Общий CRUD уже имеет отдельную ветку обновления по `id` с `RETURNING`, но upload использует ORM-ветку `db_obj`; таблица `log` и схема `LogCreate` требуют существующий `account_id`. Пользователь подтвердил, что префикс имени соответствует `number`, часть после `_` является timestamp, целостность файлов не проверяется, одновременные операции над одним аккаунтом отсутствуют, а старое и новое имена при upload различны. Скоуп ограничен этим endpoint, необходимыми CRUD-операциями, nullable-ссылкой журнала и отдельным скриптом восстановления; другие API, разрешение дублей и общий журнал всех операций не изменяются.

## Требования

### Функциональные требования

1. **FR-01.** Сохранить URL, API Key-аутентификацию, multipart-контракт и ответ `201` со схемой `AccountExternal` для создания и обновления. Не менять глобальный поиск аккаунта по номеру, присваивание владельца, генерацию UUID, формат имён и действующую семантику непустого `hash`.
2. **FR-02.** Сохранить новый архив и переданный профиль до транзакции изменения аккаунта. Обновлять выбранную строку по `id` через `UPDATE ... RETURNING`, проверить наличие результата и совпадение возвращённого `file_name` с новым именем до commit; отсутствие строки или несовпадение должны приводить к rollback без удаления старых файлов.
3. **FR-03.** При обновлении не заменять непереданные обязательные поля БД на `None`; для доступного в `AccountUpload` поля `type` отсутствие в исходной форме означает сохранение прежнего значения. При создании без `type` использовать существующий default модели `1`; явно переданное пустое/`None` значение обязательного поля отклонять до записи файлов. Обязательные параметры самого API, включая `number` и `file`, остаются обязательными, а общая обработка `None` в `CRUDBase` не меняется.
4. **FR-04.** Удалять прежний архив и профиль только после подтверждённого commit новой ссылки и только если соответствующее старое имя больше не используется аккаунтами. Уже отсутствующий старый файл пропускать; ошибка очистки после commit должна фиксироваться как ошибка этого этапа, не откатывать аккаунт и не превращать зафиксированное обновление в мнимую неудачу записи БД. При неподтверждённом исходе commit не удалять ни старые, ни новые файлы.
5. **FR-05.** Ошибки прикладных этапов upload записывать в `log` с `event=account.error` и `source=ext_api` через новую сессию и отдельную транзакцию после завершения основной транзакции. Контекст должен содержать безопасные параметры запроса, метаданные файлов, идентификатор операции, выбранный аккаунт и старые/новые имена, этап, сведения об ошибке и исход БД; байты файлов, ключи доступа, пароли, значение `hash` и SQL-параметры исключаются. Отказ самой записи ошибки не должен подменять первичное исключение или запускать рекурсивное журналирование: используется безопасный аварийный вывод в существующий серверный лог.
6. **FR-06.** Разрешить `log.account_id=NULL` в ORM-модели, `LogCreate`, сервисе записи и БД, сохранив FK, индекс и действующее `ON DELETE CASCADE` для ненулевых ссылок. Для незафиксированного создания использовать `account_id=NULL`, сохраняя номер и возможный выделенный ID только в контексте; после подтверждённого commit можно ссылаться на созданный аккаунт. Downgrade не должен удалять или перепривязывать записи журнала: при наличии NULL он останавливается с понятной ошибкой до изменения ограничения.
7. **FR-07.** Скрипт восстановления обрабатывает только аккаунты с непустым `file_name`, для которых допустимый файл внутри выбранного каталога отсутствует. Аккаунты без имени и аккаунты с существующим точным файлом остаются без изменений; содержимое архивов не читается и не валидируется.
8. **FR-08.** Для каждого такого аккаунта выбирать максимальный числовой timestamp среди существующих архивов `<number>_<timestamp>.tar.gz`, на полное имя которых не ссылается ни один аккаунт независимо от владельца или статуса. Сначала исключаются занятые файлы, затем выбирается максимальный timestamp; отсутствие свободной альтернативы означает пропуск. Дополнительное условие «timestamp больше, чем в отсутствующем исходном имени» не вводится: согласованное правило — максимум среди свободных альтернатив.
9. **FR-09.** Восстановление выполняется последовательно, с короткой транзакцией на одну строку и проверкой результата изменения; меняется только `file_name`, включая явное сохранение прежнего `updated_at`. Перед изменением повторно проверяются исходная ссылка и отсутствие ссылок на кандидата, после успешного commit кандидат исключается из свободных для всего оставшегося запуска. Скрипт не удаляет, не переименовывает файлы и не объединяет дубли аккаунтов.
10. **FR-10.** Скрипт использует настройки подключения приложения, поддерживает `--upload-dir` и безопасный предварительный режим `--dry-run`, выводит счётчики и результат назначения с ID, старым и новым именем без секретов. Обычный запуск выполняет восстановление, `--dry-run` не выполняет записывающий SQL; повторный запуск не меняет уже восстановленные строки. При ошибке выводится честный частичный итог с ненулевым кодом завершения, ранее подтверждённые commit не объявляются отменёнными.

### Нефункциональные требования

1. SQL остаётся в CRUD-слое, commit управляется вызывающей операцией, а длительное файловое I/O выполняется асинхронно либо через `asyncio.to_thread`, вне активной SQL-транзакции. Не добавлять зависимости, общую файловую платформу или рефакторинг остальных обработчиков.
2. Независимое журналирование не использует сломанную бизнес-сессию; его JSON-контекст состоит из сериализуемых снимков, а не живых ORM-объектов, исключений или `UploadFile`. Исходный результат SQL и факт доставки HTTP-ответа клиенту не смешиваются.
3. Каталог восстановления индексируется один раз, кандидаты группируются и сортируются по номеру, аккаунты и ссылки читаются ограниченными порциями с keyset-пагинацией. Не сканировать весь каталог заново для каждой строки и не удерживать транзакцию на время полного обхода диска.
4. Проверки выполняются с временными файлами, моками внешних зависимостей и отдельной тестовой PostgreSQL. Реальную независимость транзакций, `RETURNING` и миграцию необходимо подтвердить на PostgreSQL, а не только проверкой вызовов моков.
5. Рабочие архивы и production-БД не используются при тестировании; запуск записывающего восстановления требует отдельного решения оператора после предварительного отчёта и резервного копирования. Права чтения логов, общие настройки приложения и проектные спецификации не изменяются молча.

## Технические детали реализации

1. **Координатор upload и границы транзакций.** После аутентификации сохранить необходимые скалярные данные пользователя, прочитать существующий аккаунт в короткой предварительной транзакции и получить независимый снимок полей через репозиторий, без удержания ORM-объекта `Account` в identity map основной операции. Завершить эту транзакцию до файловой записи, поскольку даже SELECT запускает `autobegin`; затем записать новые файлы и открыть отдельную короткую транзакцию изменения. Для UPDATE переиспользовать `CRUDBase.update` с аргументом `id`, `returning="object"` и `commit=False`, а не ветку `db_obj`; проверить ID и новое имя именно по SQL-результату, избегая устаревшего ORM-кэша. Нормальный доменный аудит `account.create`/`account.update` и подготовка DTO ответа выполняются до общего commit, чтобы последующая очистка не запускала ленивые SQL-запросы или сериализацию из просроченного объекта.
2. **Подготовка значений и присутствие полей.** Внутри upload получить набор реально переданных полей из уже разобранной формы, не перечитывая файловые байты и не меняя общий `deps.as_form`. Этот адаптер передаёт default-значения в конструктор модели, поэтому `model_fields_set` и `exclude_unset` сами по себе не доказывают отсутствие поля у клиента. Сформировать данные обновления локально: пропущенный `type` исключить из UPDATE, явно пустой отклонить до файловой записи, а при создании не передавать искусственный `None` вместо default. Прочие nullable-поля, отсутствие нового профиля, присваивание владельца и `_apply_upload_hash` сохраняют нынешнюю семантику; глобальный `exclude_none` не вводится.
3. **Сохранение и последующая очистка файлов.** Прежние имена, новый путь и результаты каждой файловой операции сохраняются в снимке состояния операции; ранее существовавшие архив и профиль остаются нетронутыми до commit. После подтверждённого commit репозиторий проверяет ссылки на прежние имена, эта читающая транзакция закрывается, и только затем выполняется удаление неиспользуемых файлов; отсутствие старого файла и наличие других ссылок считаются пропуском, а не отказом обновления. Ошибка удаления журналируется с подтверждённым состоянием БД, после чего возвращается обычный успешный ответ; при сбое до commit новые файлы автоматически не удаляются, чтобы не потерять данные при неопределённом исходе фиксации. Совпадение старого и нового имени и параллельные изменения исключены условиями задачи, поэтому новый алгоритм имён, распределённые блокировки и механизм повторов не проектируются.
4. **Независимая запись ошибки.** В `LogService` добавить отдельный метод записи через собственный `async_session`, не меняющий транзакционные свойства существующих `record`/`records`; endpoint вызывает его только после rollback/закрытия основной транзакции либо после уже подтверждённого commit. Контекст содержит `operation_id`, метод и маршрут, разрешённые значения и присутствие параметров формы, filename/content-type/размер переданных файлов, выбранную ветку create/update, исходные и запрошенные значения, этап (`lookup`, `validate`, `write_archive`, `write_profile`, `db_write`, `verify_returning`, `commit`, `cleanup`), класс ошибки, безопасное описание, SQLSTATE/ограничение при наличии и состояние `not_committed`/`committed`/`unknown`. Значение `hash`, авторизационные данные, содержимое архивов, сырой SQL с параметрами и необработанные сообщения драйвера с полной строкой данных не сохраняются; UUID, даты и пути предварительно преобразуются в JSON-совместимые значения. Для нового аккаунта с неподтверждённым commit FK остаётся NULL, а сбой журналирования сообщается через существующий logger без маскировки первичной причины.
5. **Последовательное восстановление.** Переиспользовать проверку допустимого файла из `app.utils.account_files`, правила индексации и разбора timestamp из существующих диагностических скриптов, не переписывая их; запросы чтения и условного изменения добавить в `AccountCRUD`. Читать строки по `id DESC` ограниченными порциями и собрать глобальное множество занятых имён; для равных числовых timestamp использовать стабильный порядок по полному имени, не меняющий приоритет timestamp. Проверки файлов выполнять до короткой записывающей транзакции, а в ней повторно удостовериться, что исходная ссылка не изменилась и кандидат свободен, выполнить UPDATE с проверяемым результатом и сохранить `updated_at` по образцу `update_hash`. После commit обновить множество занятых имён; в `--dry-run` выполнить то же резервирование только в памяти, чтобы прогноз не назначал один файл двум строкам. Не импортировать `app.main`, не запускать lifespan/jobs/init_db; при ошибке остановить записывающий проход, освободить сессии/engine и сообщить уже выполненные изменения.
6. **Совместимость nullable-журнала и миграции.** `LogBase` и схема ответа уже допускают отсутствие аккаунта, но `LogCreate`, ORM-колонка и сигнатура сервиса требуют изменения; существующие FK, каскады и правила доступа сохраняются. Новая ревизия должна следовать за фактической текущей головой; по просмотренным исходникам это `8c4e1f7a2b90`, а revision ID следует сгенерировать при реализации, не выдумывать в плане. Upgrade снимает `NOT NULL`, downgrade возвращает его только после проверки отсутствия NULL и не удаляет диагностические события. История миграций не создаёт начальную схему и повторно добавляет `attempts`, поэтому доказательные тесты новой ревизии должны использовать явно подготовленную изолированную предмиграционную схему, а не предполагать рабочий полный upgrade с пустой БД.

### Изменить

- `app/api/ext/v1/account.py` меняется только в части upload и его локальных вспомогательных функций: присутствие параметров, порядок операций, сверка `RETURNING`, независимая обработка ошибок и docstring.

- [ ] Реальный UPDATE возвращает ожидаемое новое имя; отсутствующий/несовпавший результат откатывается, старые файлы удаляются только после подтверждённого commit, а сбой очистки не отменяет сохранённую ссылку.
- [ ] Ошибки прикладных этапов upload при доступной БД создают независимые `account.error`, включая `account_id=NULL` при незафиксированном создании; контекст безопасен, исход commit не искажается, отказ writer не маскирует первичную ошибку.

- Оператор должен обеспечить резервную копию затрагиваемых данных/архивов, доступ к правильному каталогу и отсутствие одновременных upload, восстановления или ручных изменений файловых ссылок в записывающий проход; производственный запуск не является частью автоматического выполнения тестов.

## Заметки

**Границы согласованного решения.** Равенство старого и нового имени, конкурентные запросы к одному аккаунту, целостность архивов, уникальность номера, смена правил владельца, исправление остальных API и общий включаемый JSONL-журнал не входят в эту задачу. `account.error` не требует нового ENV-переключателя: вместо прежнего широкого предложения реализуется последнее согласованное требование записи ошибок именно upload в таблицу `log`.

**Граница ошибок HTTP.** Запись `account.error` охватывает прикладные этапы после успешной аутентификации и входа в обработчик, включая его проверку расширения и обязательных значений. Ошибки аутентификации, повреждённого multipart и стандартная валидация FastAPI до вызова endpoint остаются в существующей обработке; глобальный middleware или перехватчик всех HTTP-ошибок не добавляется.

**Видимость и сохранность событий.** Существующий `GET /api/v1/logs/` ограничивает обычного пользователя владельцем связанного аккаунта, поэтому события с `account_id=NULL` видны superuser, но не становятся автоматически доступны обычному пользователю по `log.user_id`. Действующий `ON DELETE CASCADE` ненулевой ссылки сохраняется; nullable-колонка сама по себе не превращает журнал в неудаляемый аудит. Сырой ID, выделенный незафиксированной вставке, не должен попадать во внешний ключ ошибки.

**Проверки для code-агента.** При явно настроенном тестовом окружении запустить `python -m pytest tests/api/ext/v1/test_account_upload.py tests/test_log.py tests/test_log_account_id_migration.py tests/test_restore_missing_files.py`, затем `python -m pytest tests/integration/test_account_archive_transactions.py` и регрессии `python -m pytest tests/api/ext/v1/test_account_hash.py tests/api/ext/v1/test_session_device.py tests/api/v1/test_account_missing_files.py tests/test_missing_files.py tests/test_missing_files_alt.py`. Доказательные тесты PostgreSQL нельзя объявлять пройденными по наличию unit-моков или молча пропускать при отсутствии тестовой БД; отсутствие окружения фиксируется как блокер приёмки. В этом плане проверки только назначены, не выполнены.

**Операторский запуск после реализации.** Сначала выполнить `docker compose exec api python /app/restore_missing_files.py --dry-run` в согласованном окружении и проверить назначения; `--upload-dir` использовать при нестандартном расположении хранилища. Команда `docker compose exec api python /app/restore_missing_files.py` изменяет БД и допускается только после отдельного подтверждения оператора и резервного копирования. Предпросмотр является операционной защитой, не проверкой содержимого архивов и не автоматическим разрешением записывающего запуска.

**Нерешённые эксплуатационные вопросы.** До реализации нужно определить доступное изолированное PostgreSQL-окружение, а до выпуска подтвердить реальную ревизию и схему БД; это не установлено чтением исходников. Срок и окно производственного восстановления выбирает оператор. Иных уточнений основных правил выбора альтернативы, NULL-ссылки и последовательности upload для подготовки этого плана не требуется.
