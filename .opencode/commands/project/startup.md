Загрузить скилы `project-context` и `template-system` перед началом.

Заполнить проектную документацию через управляемый диалог с пользователем. Применять эту команду, когда кодовая база не содержит достаточной информации для автоматического анализа или при создании нового проекта с нуля.

## Структура диалога

Вести диалог последовательными группами. После каждой группы представить контент, который будет записан, и запросить подтверждение перед продолжением.

### Группа 1: Обзор

Установить идентичность проекта:
1. Что делает проект? (запросить 2-3 предложения)
2. Какую проблему решает и какую ценность обеспечивает?
3. Какой тип проекта? (Backend API / Веб-приложение / CLI инструмент / Библиотека / Мобильное приложение / Десктопное приложение / Data pipeline / Другое)
4. К какой экосистеме или платформе принадлежит? (соседние сервисы, инфраструктура)

Целевой файл: `overview.md`

### Группа 2: Технологический стек

Определить техническую основу:
1. Язык и runtime (с версией, если известна)
2. Основной фреймворк
3. База данных (или «отсутствует»)
4. Система messaging или событий (или «отсутствует»)
5. Подход к аутентификации (или «отсутствует»)
6. Тестовый фреймворк
7. Инфраструктура и инструменты деплоя

Целевой файл: `stack.md`

### Группа 3: Архитектура

Определить структурный дизайн:
1. Архитектурный стиль (слоистая, гексагональная, модульный монолит, микросервисы, событийная, другое)
2. Основные компоненты или слои и их ответственности
3. Как типичный запрос или операция проходит через систему
4. Как обрабатываются и распространяются ошибки

Целевой файл: `architecture.md`

### Группа 4: Структура репозитория

Описать раскладку кодовой базы:
1. Основные директории и их назначение
2. Как организован исходный код внутри главной директории
3. Где располагаются тесты и как они структурированы
4. Как управляется конфигурация и настройки окружения

Целевой файл: `structure.md`

### Группа 5: Конвенции

Зафиксировать инженерные стандарты:
1. Каких инженерных принципов придерживается команда?
2. Существуют ли устоявшиеся соглашения по именованию?
3. Каковы ожидания по тестированию нового кода?
4. Какие практики явно запрещены?

Целевой файл: `conventions.md`

### Группа 6: Ограничения и интеграции

Задокументировать границы и внешние зависимости:
1. Технические ограничения (runtime, платформа, требования к производительности)
2. Архитектурные границы, которые не допускается нарушать
3. Требования совместимости для API или форматов данных
4. Внешние системы, с которыми интегрируется проект (название, назначение, протокол)

Целевые файлы: `constraints.md`, `integrations.md`

## Правила диалога

- Предлагать варианты ответов, где это уместно, всегда включая вариант «Другое»
- Если пользователь отвечает неформально, переформулировать ответ в точный технический язык перед записью
- Разрешать пропуск любой группы; отметить пропущенные файлы как `status: partial`
- Не навязывать конкретную архитектуру или технологический стек
- Не выдумывать информацию, которую пользователь не предоставил

## После завершения диалога

1. Заполнить проектные файлы в соответствии с правилами скила `template-system`, соблюдая все стандарты качества контента
2. Удалить маркеры шаблонов из каждой заполненной секции
3. Установить frontmatter `status` для каждого файла в соответствии со степенью заполнения
4. Добавить запись в `changes.md`, документирующую инициализацию
5. Представить сводку: что заполнено и что осталось пустым
