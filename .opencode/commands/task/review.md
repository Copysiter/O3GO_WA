Загрузить скил `project-context` перед началом.

Провести структурированное ревью реализации задачи для оценки качества, корректности и полноты.

## Использование

```
/task/review [путь-к-плану | описание скоупа]
```

При указании пути к плану ревью валидирует реализацию на соответствие требованиям плана. При отсутствии аргумента ревью охватывает недавние изменения, выявленные через git diff.

## Шаг 1: Определение скоупа

**При наличии ссылки на план:**
1. Прочитать файл плана и извлечь критерии приёмки
2. Определить затронутые файлы из секции affected_areas
3. Получить git diff, ограниченный этими файлами

**Без плана (недавние изменения):**
1. Получить список модифицированных файлов: `git diff --name-only`
2. Просмотреть недавнюю историю коммитов: `git log --oneline -5`

## Шаг 2: Анализ граничных случаев

Исследовать изменённые файлы для выявления рисков, не видимых в diff:
- Файлы, зависящие от модифицированных интерфейсов, но не затронутые изменениями
- Пути потоков данных, проходящие через изменённый код и способные проявить новые режимы отказа
- Граничные условия: пустые входные данные, максимальные значения, null или undefined состояния
- Вопросы конкурентности: гонки состояний, мутации разделяемого состояния
- Пути распространения ошибок через изменённый код

## Шаг 3: Оценка качества

Оценить реализацию по стандартам проекта:

**Корректность:** Достигает ли код заявленной цели? Обработаны ли все пути выполнения? Учтены ли ошибочные состояния?

**Конвенции:** Соответствует ли реализация `.opencode/project/conventions.md` и `.opencode/project/constraints.md`? Согласуется ли с паттернами из `.opencode/project/architecture.md`?

**Безопасность:** Присутствует ли валидация входных данных? Отсутствуют ли секреты в коде? Применяются ли проверки аутентификации и авторизации?

**Производительность:** Выявляются ли узкие места, неэффективные запросы или некорректная асинхронная обработка?

## Шаг 4: Соответствие плану (при наличии плана)

- Выполнены ли все критерии приёмки?
- Реализованы ли все запланированные фазы?
- Остаётся ли реализация в рамках определённого скоупа?

## Шаг 5: Верификация

Выполнить верификационные команды и зафиксировать их вывод:
```bash
pytest / npm test / go test ./... / cargo test
python -m build / npm run build / go build ./... / cargo build
ruff check / npm run lint / go vet ./... / cargo clippy
```

Не характеризовать результаты без выполнения команд. Фиксировать фактический вывод.

```markdown

### Соответствие плану
- [x] {критерий выполнен}
- [ ] {критерий не выполнен}: {пояснение}

### Выявленные граничные случаи

**Высокий приоритет:**
- {файл:строка}: {описание}. Рекомендуемое исправление: {руководство}

- {практика, заслуживающая внимания}

### Результаты верификации

### Приоритизированные рекомендации
```

## Правила

- Не модифицировать код — исключительно анализировать и рекомендовать
- Выполнять верификационные команды до формирования отчёта
- Приоритизировать находки по потенциальному влиянию, а не по количеству
- Предоставлять точные ссылки на файлы с конкретными рекомендациями по исправлению
- Отмечать образцовые практики наряду с выявленными недостатками
- Формулировать оценки прямо, без смягчения критических заключений
