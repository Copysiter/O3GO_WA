Загрузить скилы `template-system` и `project-context` перед началом.

Сформировать структурированный план реализации на основе описания задачи.

## Использование

```
/task/plan [--опции] [TASK-ID] описание задачи
```

## Опции

**Тип (опционально, автоопределение по умолчанию):**
- `--feature` — новая функциональность
- `--bugfix` — исправление дефекта
- `--refactor` — структурное улучшение
- `--task` — общая задача (по умолчанию при отсутствии совпадений)

**Режим (опционально):**
- `--fast` — компактный план в чате без создания файлов на диске
- `--full` — полный план со структурой директорий и фазированным выполнением

При отсутствии указания режима определить автоматически по масштабу задачи:
- Ясный scope, затрагивающий 1-3 файла → fast
- Несколько модулей, архитектурные решения, сквозные зависимости → full

**TASK-ID (опционально):**
- Формат: `[FRCL-123]`, `[ACC-456]`, `[FMU-789]`
- При наличии используется как имя директории плана
- При отсутствии применяется `{YYMMDD}-{slug}`

## Автоопределение типа

Сканировать описание (без учёта регистра) на характерные ключевые слова:

**feature:** добавить, создать, реализовать, новый, фича, add, create, implement, build, new, feature

**bugfix:** исправить, починить, баг, ошибка, сломано, падает, fix, bug, error, broken, crash

**refactor:** рефакторинг, улучшить, оптимизировать, очистить, вынести, refactor, improve, optimize, clean, extract

При отсутствии совпадений назначить тип `task`.

## Режим fast

Не создавать файлы на диске. Прочитать `.opencode/templates/task/task.template.md` как структурный ориентир для обеспечения полноты.

Обязательные секции в выводе:

1. **Описание** — что выполняется и с какой целью (на основе секций «Описание» и «Цель» шаблона)
2. **Скоуп изменений** — файлы для создания или модификации (на основе секции «Скоуп изменений»)
3. **Шаги** — нумерованные конкретные действия (на основе секции «Фазы реализации», одна фаза)
4. **Критерии приёмки** — чекбоксы верификации (на основе секции «Критерии приёмки»)

Включить опциональные секции при наличии оснований:
- Технические детали (при наличии архитектурного решения)
- Риски (при наличии неочевидных режимов отказа)

Формат вывода:

```markdown
## План: {описание}

**Тип:** {feature/bugfix/refactor/task}

### Описание
{2-3 предложения: что и с какой целью}

### Скоуп изменений
- `path/to/file.ext` — что изменить и почему
- `path/to/other.ext` — что изменить и почему

### Шаги
1. {конкретное действие}
2. {конкретное действие}
3. {конкретное действие}

### Критерии приёмки
- [ ] {верифицируемый критерий}
- [ ] {верифицируемый критерий}
- [ ] {верифицируемый критерий}
```

Завершить вопросом: «Приступить к реализации? (переключитесь на code-агента)»

## Режим full

### Шаг 1: Именование директории

- С TASK-ID: `plans/{TASK-ID}/`
- Без TASK-ID: `plans/{YYMMDD}-{slug}/`

Slug формируется из описания: 2-5 слов, kebab-case, всегда на английском.
Slug используется только при отсутствии TASK-ID.

Получение текущей даты: `date +%y%m%d`

Примеры:
- `/task/plan [FRCL-480] Добавить OAuth2 аутентификацию` → `plans/FRCL-480/`
- `/task/plan [ACC-12] Исправить ошибку пагинации` → `plans/ACC-12/`
- `/task/plan Добавить страницу профиля` → `plans/260329-user-profile-page/`

### Шаг 2: Сбор контекста

1. Прочитать `.opencode/project/overview.md`, `architecture.md`, `conventions.md`, `constraints.md`
2. При необходимости изучить релевантный исходный код для понимания существующих паттернов
3. Прочитать `integrations.md`, если задача затрагивает взаимодействие с внешними системами

### Шаг 3: Генерация плана из шаблона

1. Прочитать шаблон `.opencode/templates/task/task.template.md`
2. Применить правила скила `template-system` с полным соблюдением стандартов качества контента:
   - Изучить `[TEMPLATE_GUIDE]` для понимания ожидаемого объёма и формата каждой секции
   - Изучить `[TEMPLATE_EXAMPLE]` для калибровки уровня детализации
   - Строго соблюдать ограничения формата (количество предложений, размер списков)
   - Заменить каждый `{{placeholder}}` сгенерированным контентом
   - Удалить все блоки `[TEMPLATE_GUIDE]` и `[TEMPLATE_EXAMPLE]`

3. Обязательные секции — заполнить все:
   - **Описание** (`{{summary}}`) — суть задачи и её назначение (2-3 предложения)
   - **Цель** (`{{goal}}`) — измеримый результат, определяющий завершение (1-2 предложения)
   - **Функциональные требования** (`{{functional}}`) — тестируемые требования (3-10 пунктов)
   - **Нефункциональные требования** (`{{non_functional}}`) — качественные характеристики (2-5 пунктов)
   - **Скоуп изменений** (`{{scope}}`) — файлы для создания/изменения/удаления (группировка по действию)
   - **Фазы реализации** (`{{phases}}`) — 2-5 фаз, каждая содержит 2-6 чекбокс-шагов
   - **Критерии приёмки** (`{{checks}}`) — бинарные проверки (3-8 чекбоксов)

4. Опциональные секции — заполнить при наличии оснований:
   - **Контекст** (`{{context}}`) — предыстория, существенная для понимания задачи
   - **Технические детали реализации** (`{{solution}}`) — архитектурные решения и паттерны
   - **Риски** (`{{risks}}`) — потенциальные режимы отказа и стратегии митигации
   - **Зависимости** (`{{dependencies}}`) — предусловия, которые должны быть выполнены
   - **Заметки** (`{{notes}}`) — открытые вопросы или решения, требующие уточнения

5. Установить frontmatter:

```yaml
---
title: "{краткий заголовок}"
description: "{одно предложение для превью}"
type: feature|bugfix|refactor|task
task_id: FRCL-480  # или пусто
status: planned
priority: P2
created: YYYY-MM-DD
---
```

6. Сохранить как `plans/{dirname}/plan.md`

### Шаг 4: Итоговый вывод

```markdown
## План создан

**Путь:** plans/{dirname}/plan.md
**Тип:** {type}
**Фаз:** {количество}

### Фазы
1. {название фазы} — {краткое описание скоупа}
2. {название фазы} — {краткое описание скоупа}
3. {название фазы} — {краткое описание скоупа}

Для реализации: переключитесь на code-агента и выполните `/task/do plans/{dirname}/plan.md`
```

## Правила

- Не реализовывать код — формировать исключительно план
- Не выдумывать требования — при недостатке информации запросить уточнение у пользователя
- Соблюдать конвенции и ограничения проекта из `project-context`
- Проектировать фазы как независимо завершаемые и тестируемые единицы
- Формировать slug на английском языке вне зависимости от языка описания
- Представлять каждый шаг внутри фазы как чекбокс `- [ ]` для отслеживания прогресса
