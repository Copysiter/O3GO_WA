# Архитектура

## Архитектурный стиль

Слоистая архитектура с разделением на API, CRUD-слой, модели и инфраструктуру.
Каждый слой имеет чёткую зону ответственности: API принимает запросы и валидирует входные данные, CRUD инкапсулирует доступ к базе данных, модели определяют структуру таблиц, сервисы координируют поперечные задачи.

Зависимости направлены внутрь: обработчики импортируют CRUD и сервисы, CRUD оперирует моделями через адаптер базы данных. Основная бизнес-логика находится в обработчиках API; read-only аналитика статистики реализована в StatsService.

---

## Основные компоненты или слои

- **API административное** (`app/api/v1/`) — REST-эндпоинты для управления пользователями, аккаунтами, сессиями, сообщениями, Android-устройствами, версиями, логами и опциями, а также read-only stats summary/live; аутентификация через JWT; маршрутизация через `api_router`
- **API внешнее** (`app/api/ext/v1/`) — интеграционные эндпоинты для загрузки/получения аккаунтов, управления сессиями (start/finish/ban), создания и обновления статусов сообщений, генерации HTML-отчётов; аутентификация через API Key
- **CRUD-слой** (`app/crud/`) — обобщённый репозиторий `CRUDBase` с поддержкой фильтрации через fastapi-filter, массовых операций (insert, map_update), upsert; конкретные репозитории для каждой доменной сущности
- **Модели** (`app/models/`) — SQLAlchemy ORM-модели: User, Account, Session, Message, Android, Log, Version; определения статусов через IntEnum
- **Схемы** (`app/schemas/`) — Pydantic-схемы для валидации входных данных и сериализации ответов; фильтры на базе fastapi-filter
- **Сервисы** (`app/services/`) — LogService для нормализации событий и общего независимого аудита ошибок upload/start/finish/ban, MessageService — HTTP-клиент к внешнему Message API, StatsService — период, область доступа, агрегаты summary/live и качество подсчёта сохранённой истории
- **Планировщик задач** (`app/jobs/`) — APScheduler с декоратором-реестром для регистрации задач; текущие задачи: освобождение неактивных аккаунтов и сессий
- **Адаптеры** (`app/adapters/`) — адаптер базы данных: создание async-движка, sessionmaker, базовый класс моделей
- **Инфраструктура** (`app/core/`) — конфигурация (5 групп настроек через pydantic-settings), логирование, безопасность (хеширование паролей, JWT), утилиты
- **Зависимости** (`app/deps.py`) — FastAPI-зависимости: get_db, get_current_user, get_user_by_api_key, get_basic_auth_user, as_form
- **HTML-дашборд** (`html/dashboard/`) — `DashboardApi` для stats/options и контроллер `dashboard.js` с независимыми каналами summary/live/users, восемью карточками и шестью графиками Kendo
- **Общий frontend** (`html/static/auth.js`, `html/static/script.js`) — хранение и проверка token, общий header/Drawer и logout для административных страниц

## Границы ответственности

Обработчики API принимают HTTP-запрос, валидируют параметры через Pydantic-схемы, проверяют аутентификацию и авторизацию, вызывают CRUD-операции и сервисы, формируют ответ. На текущем этапе обработчики содержат значительную часть бизнес-логики: проверку уникальности, каскадные обновления, управление файлами.

CRUD-слой является основным слоем SQL-доступа к доменным данным. Базовый класс `CRUDBase` предоставляет типизированные методы get, list, count, create, insert, update, map_update, upsert, delete с поддержкой фильтрации и пагинации. Конкретные репозитории наследуют базовый класс и привязывают модель и класс фильтра. `UserCRUD.get_options` выбирает только публичные text/value; API назначает область member по User.id, а admin получает также неактивных пользователей. Подпись использует name, затем login, затем `Пользователь {id}`, сортировка выполняется по lower(label) и id.

Сервисы реализуют поперечную функциональность, не привязанную к одному эндпоинту. LogService нормализует статусы и записывает события аудита. MessageService — HTTP-клиент к внешнему сервису сообщений.

`LogService` (`app/services/log.py`) централизует аудит `account.error` внешнего upload и `session.error` внешних start/finish/ban. `LogService.operation` создаёт отдельный для запроса dataclass `LogOperation`: это только состояние операции — action, скалярный user_id, UUID, stage, db_outcome, код ошибки, доверенные/новые FK и результат освобождения транзакции. Методы освобождения, построения контекста, независимой записи и диагностики принадлежат LogService. Прежний модуль `app/services/session_error.py` удалён. В upload остаются состояние обработчика и тонкий callback, делегирующий метаданные в `LogService.upload_details`; сессионные вызовы обходятся без request-details. Унификация охватывает upload/start/finish/ban; legacy-логирование остальных account-эндпоинтов сохраняется.

StatsService (`app/services/stats.py`) реализует `resolve_period` для UTC-интервала, календарного предела и сравнения, асинхронный `resolve_scope` для self/admin-all/admin-selected, а также `get_summary` и `get_live`. Выбранный администратором пользователь проверяется через существующий `UserCRUD.get`. Каждый агрегат выполняется одним CTE SELECT: summary объединяет оба периода, cohort, первые сохранённые свидетельства сообщений/ошибок и audit gaps в одном snapshot, live использует фактический `statement_timestamp()`. Сервис считает сохранённые данные без ручных дат начала сбора и собирает DTO из `app/schemas/stats.py`; для admin-all и scoped используются две фиксированные SQL-формы с bind-параметрами. История ошибок агрегируется JOIN по event/user/operation_id с прямыми event/source/user-фильтрами, а не LATERAL-запросом для каждой операции. Первое свидетельство ищется по всей сохранённой истории до применения границ отчёта. Для lifecycle, сообщений и live область определяется текущим владельцем аккаунта; для error-групп — сохранённым вызывающим пользователем в `log.user_id`, независимо от текущих account/session FK.

Пользователь одобрил узкое исключение из правила размещения SQL в CRUD: только read-only аналитические SELECT внутри StatsService, без `FOR UPDATE`, commit, записывающих SQL и изменений ORM-сущностей. Реализованный поток: API stats → StatsService → существующий CRUD для scope / SQLAlchemy и адаптер БД для агрегатов. Отдельный пакет запросов, ORM-сущность и CRUD статистики не вводятся; исключение не распространяется на остальные сервисы.

Код summary/live и маршруты фазы 3 плана `plans/261003-dashboard-backend/plan.md` готовы. Фаза 4 завершена в коде и локальной верификации после одобренных пользователем исправлений общего auth/header и регрессионных проверок. Локальная приёмка явно одобренной фазы 5 выполнена, первые два пункта завершены. Третий пункт выполнен частично: локально проверены snapshot, основные сессионные операции и неизменность собственной тестовой схемы, но рабочие metadata и стоимость на согласованном репрезентативном объёме остаются открытыми. Последующее прямое поручение пользователя от 2026-10-05 реализовано как унификация аудита в LogService и удаление ручной coverage-конфигурации; прежнее требование подтверждать даты начала сбора отменено. Rollout и подтверждение работы аудита на всех обслуживающих workers остаются открытыми; `plans/261003-dashboard-backend/rollout.md` подготовлен, но не выполнен. Общая реализация остаётся `in_progress`.

Историческая локальная приёмка фазы 5 до унификации проверяла архитектуру без изменения runtime-кода. Независимые контрольные SQL сверяют метрики, периоды, buckets, cohort, доставляемость и live через реальные stats-маршруты на изолированной PostgreSQL. Тестовая advisory CTE оборачивает неизменённый service SELECT с сохранением типизированных bind-параметров и подтверждает единый snapshot через конкурентный commit для scoped/admin-all; следующий SELECT без обёртки видит новые данные в той же READ COMMITTED-транзакции. Отдельно прямые вызовы настоящих start на существующем аккаунте → finish → ban → ban выполняются одновременно с обычными stats-чтениями, сохраняя реальные CRUD, статусы, аудит и attempts. После унификации добавлены реальные upload-транзакции и повторена расширенная выборка регрессий. Каталоги сравниваются до/после только внутри собственной UUID-схемы; это не проверка production parity, HTTP/auth-конкурентности или нагрузочного SLA. Полные результаты и команды ведутся в плане, ограничения — в `constraints.md`.

Модели определяют структуру таблиц и отношения между сущностями. Схемы определяют контракт API-запросов и ответов. Инфраструктура предоставляет конфигурацию, логирование и инструменты безопасности.

### HTML-дашборд и общая авторизация

`DashboardApi` (`html/dashboard/js/api.js`) выполняет только фиксированные GET к `/api/v1/stats/summary`, `/api/v1/stats/live` и `/api/v1/options/user` через существующий `api_base_url`. Каждый запрос читает актуальный Bearer token через `getToken`, имеет timeout 20 секунд и отменяемый handle. Перед обработкой успеха и ошибки проверяются актуальность credentials и отмена; успешный ответ дополнительно сопоставляется с ожидаемой областью, а summary — также с запрошенным периодом. Явная проекция snake_case → camelCase сохраняет `null`, отдельные event/cohort datasets и серверную доставляемость; бизнес-агрегаты SQL на клиенте не воспроизводятся.

Интерфейс поясняет, что статистика рассчитана по сохранённым событиям: ноль означает отсутствие записанных событий, а не доказанное отсутствие прошлой активности. Предупреждения о качестве подсчёта и отображение `null` сохранены. Адаптер принимает прежнее ненулевое поле coverage `from` для совместимости, но UI не выводит его как гарантированную дату начала сбора.

`dashboard.js` управляет отдельными запросами и revision guards summary/live/users. Выбранный владелец обновляется до валидации периода и не зависит от успеха summary; при смене владельца прежние карточки, графики, live и диалог очищаются. Live обновляется каждые 60 секунд независимо от дат и не запускает второй таймерный запрос поверх pending-запроса. `pagehide` отменяет работу и отключает timers/observer; persisted `pageshow` возобновляет её один раз, включая незавершённую загрузку options даже при невалидном периоде.

`auth.js` сохраняет синхронные `getToken`/`setToken` и объект `window.isAuth` с четырьмя полями `access_token`, `token_type`, `ts`, `user`; поддерживаются фактический lowercase `bearer` и прежние timestamps без timezone. Некорректные данные storage безопасно очищаются. `setToken(null)` очищает cached/stored token и инвалидирует старую revision. Каждый `POST /api/v1/auth/test-token` использует свежий снимок storage; обе ветки ответа проверяют revision запроса и fingerprint token/type/user ID/role/active. Обновление только `ts` не считается новым входом. Для auth действует один таймер 60 секунд и timeout запроса 20 секунд.

Общий DOM-ready обработчик в `script.js` повторно читает token и проверяет его на `null`. Разметка Kendo header статична, имя добавляется через `.text()` с fallback name → login → `Пользователь {id}`; HTML и выражения Kendo в имени остаются текстом. Logout использует `setToken(null)`. Эти исправления не являются переработкой credential caches остальных legacy grids; backend авторизации в фазе 4 не менялся.

В сохранённой пользователем версии `html/static/script.js` (`4956e7b`) `dashboardNavigation1` равен пустой строке: ссылка на дашборд скрыта в общем меню. Прямой `/dashboard/` работает. Текущая browser-проверка учитывает это поведение; унификация аудита не меняла shared script.

## Поток запроса или выполнения

```
Запрос → FastAPI → Auth (JWT / API Key) → Обработчик → CRUD / Сервис → БД → Ответ
```

Типичный поток обработки запроса в административном API:

1. FastAPI маршрутизирует запрос к соответствующему обработчику
2. Dependency injection предоставляет асинхронную сессию БД через `get_db`
3. Зависимость `get_current_active_user` верифицирует JWT-токен и извлекает пользователя
4. Обработчик валидирует входные данные через Pydantic-схему
5. Обработчик применяет бизнес-логику: проверяет уникальность, права доступа, состояние сущностей
6. CRUD-репозиторий выполняет SQL-операции (create, update, delete, list)
7. LogService записывает событие аудита (при изменении статуса)
8. Транзакция коммитится, ответ сериализуется через Pydantic-схему

Поток внешнего API отличается аутентификацией (API Key через `get_user_by_api_key`) и бизнес-логикой: эндпоинты ориентированы на интеграцию — атомарное получение аккаунта с блокировкой, создание сообщений, обновление статусов сессий.

Для stats `api_router` регистрирует `GET /api/v1/stats/summary` и `/live`. После `get_current_active_user` и валидации query DTO обработчик вызывает StatsService и сериализует результат без commit. Один аналитический statement на агрегат не исключает отдельных SELECT аутентификации и проверки выбранного владельца.

Обычный клиентский поток: `dashboard.js` → `DashboardApi` → JWT stats/options → DTO → карточки/графики/live. Только явный `?demo=1` загружает `mock_data.js` и выбирает `DashboardMock`, без запросов stats/options; общая авторизация продолжает работать. Ошибки API не переключают источник данных на mock.

## Стратегия интеграции

Внешние системы доступны через HTTP-клиент в `app/services/message/client.py`. Клиент инкапсулирует взаимодействие с Message API (campaigner.o3go.ru): получение следующего сообщения и обновление статуса.

На текущем этапе адаптеры внешних систем не вынесены в отдельный слой — HTTP-клиент находится в сервисном слое. Адаптер базы данных в `app/adapters/db/` предоставляет async-движок и sessionmaker.

## Стратегия обработки ошибок

Ошибки обрабатываются на уровне обработчиков API: бизнес-логика возвращает HTTPException с соответствующим кодом статуса (400, 401, 403, 404, 409, 422).

StatsService выдаёт типизированные ошибки `StatsPeriodError`, `StatsScopeDeniedError` и `StatsUserNotFoundError`, которые stats API отображает в HTTP 422, 403 и 404. Зарегистрированные маршруты проверены отдельно от contract-probes фазы 1; сохранены штатные auth-отказы: отсутствие токена — 401, невалидный JWT — 403, неактивный пользователь — 400.

Локальный `_StatsRoute` в `app/api/v1/stats.py` перехватывает `SQLAlchemyError`, включая ошибки auth-зависимостей и проверки выбранного владельца, и возвращает общий 503 без SQL и приватных деталей. Это не глобальный middleware; обработка других маршрутов не менялась. Диагностика через `asyncio.to_thread` передаёт logger только action и тип ошибки без сообщения/traceback, затем независимо пишет в stderr, даже если handler logger подавил I/O-ошибку. Отказы каналов, включая одновременный отказ обоих, оставляют безопасные notes в HTTPException и сохраняют ответ 503.

Дашборд показывает отдельные loading/error/unavailable состояния каналов и фиксированные безопасные сообщения вместо текста серверного ответа. Последний корректный snapshot той же области при временном сбое явно помечается как прежний; `null` при невозможности надёжно посчитать error-группу отображается как «—» и пропуски графика, а не нули. Временные сбои summary/live изолированы; отказ авторизации или несоответствие сеанса/scope останавливают каналы и очищают отображаемые данные.

Для общей проверки входа актуальные 401/403/404, 400 с `detail: "Inactive user"` либо корректный профиль с `is_active: false` очищают auth и ведут на `/auth/`. Сеть, timeout, 5xx и некорректный ответ сохраняют действующий token, выдают фиксированное безопасное предупреждение и оставляют повторную проверку по таймеру. Устаревшие ответы не могут восстановить старый вход или удалить новый token.

Внешние upload/start/finish/ban перехватывают `Exception` и `asyncio.CancelledError` и вызывают `LogService.report_error(db, error, operation=..., details=...)`. Общий корень контекста содержит `operation_id`, `action`, `user_id`, `stage`, `db_outcome`, `error` и сведения об освобождении транзакции. Общая диагностика исключает исходные сообщения исключений, SQL/параметры и произвольные OS paths; сохраняет тип, безопасный код, HTTP status, SQLSTATE/errno и имена объектов БД. Диагностические строки ограничены 160 символами, обход причин — 12 исключениями, traceback — 12 координатами с basename файла, функцией и строкой, без locals.

Сессионный аудит не копирует request-details, device/API/auth-данные или `info_*`. Upload отдельно помещает в `details` разрешённые метаданные запроса, файлов и снимков аккаунта: в том числе `number`, `type`, `limit`, `cooldown`, `geo`, `info_1..info_8`, имя/тип/размер файла, ветку, storage/cleanup и признак наличия hash. Значения hash, headers, содержимое файлов и произвольные поля запроса не копируются; разрешённые upload-метаданные могут содержать пути хранения. Это отдельный контракт от очищенной общей диагностики исключения. ID вызывающего пользователя фиксируется до первого I/O; существующие FK сохраняются скалярно после проверки владельца, новые разрешены только после подтверждённого commit, чужие не записываются.

`LogService.report_error` возвращает bool подтверждённого освобождения бизнес-транзакции, а не успешности записи аудита. Finalizer защищён через `asyncio.shield` и завершается до очистки зависимостей, включая повторные отмены; первичная ошибка и внешняя отмена сохраняются. Неподтверждённый аудит требует минимального stderr fallback независимо от поведения logger, в том числе при неожиданном отказе finalizer или защищённой задачи. Это необходимо и после commit, когда upload может вернуть HTTP 201 и не передать исключение клиенту. Отказ stderr отмечается безопасной note в исходном исключении; неподтверждённое освобождение фиксируется в операции и блокирует последующие независимые writers.

В общей технической диагностике LogService не-HTTP ошибки относятся к `E.SYSTEM.API.ERROR`, HTTP 404 — к `NOT_FOUND`, остальные 4xx — к `FAILURE`. Это классификация унифицированных операций; обработка auth/message и legacy-логирование других account-маршрутов ею не переопределяются. Обычные ошибки cleanup и success logger после подтверждённого upload commit сохраняют HTTP 201; отмена передаётся вызывающему коду. Несколько ошибок одного запроса используют один UUID операции. Бизнес-commit, переходы статусов, lifecycle-аудит и attempts, включая повторный ban, сохраняют прежнюю семантику.

Внешний HTTP-клиент (MessageService) обрабатывает сетевые ошибки: HTTPStatusError, TimeoutException — логирует и возвращает None, не прерывая выполнение.

## Управление данными и состоянием

Основное хранилище — PostgreSQL 12. Все операции с данными проходят через асинхронные сессии SQLAlchemy, создаваемые на уровне запроса через dependency injection либо отдельно для независимого аудита.

Каждый запрос получает собственную сессию. Для изменяющих операций коммит транзакции управляется обработчиком: операции выполняются с `commit=False`, а коммит вызывается явно после всех изменений (CRUD + LogService). StatsService выполняет только чтение и не вызывает commit.

Для общего аудита upload/start/finish/ban исход бизнес-транзакции начинается с `not_committed`, становится `unknown` перед ожиданием business commit и `committed` только после его успешного возврата. LogService сначала выполняет rollback, при необходимости close и проверяет отсутствие активной транзакции; при неподтверждённом освобождении независимый writer не запускается и не повторяется. После освобождения существующий `LogService.record_independent` записывает событие через CRUD в собственной сессии с собственным commit. При неизвестном исходе новые FK остаются NULL даже при фактическом сохранении бизнес-строк; доверенные существующие FK допустимы. StatsService в этом пути не участвует.

`STATS_COVERAGE_STARTS`, связанные типы/валидатор settings и пример переменной в `.env.example` удалены; `get_summary` больше не принимает `coverage_starts`. Общий RFC 3339 тип `app/core/utc.py` сохранён для UTC-контрактов DTO. Статистика по умолчанию возвращает численные значения сохранённой истории, включая нули при отсутствии записанных событий. Настройка даты сбора, фиктивные даты и backfill для этого не используются.

Wire-контракт `coverage` сохраняет группы `lifecycle`, `message_events`, `account_errors`, `session_errors`; сервис всегда возвращает `from: null`. `recorded` означает возможность подсчитать сохранённые записи, а не полноту сбора. Единственная текущая причина `partial` — `missing_operation_id`: соответствующая error-группа маскируется в NULL для всего затронутого current/previous периода и всех его buckets. Прежние причины, основанные на датах начала сбора, больше не формируются. Cohort, message_created, live, SQL/global-first, scope и правила периода сохранены; пустой диапазон даёт нули и пустой ряд.

Ручной ввод дат дашборда интерпретируется как UTC, включая часы внутри локального DST gap браузера. Клиент проверяет календарный предел месяца с ограничением дня последним днём следующего месяца; открытый конец не передаётся в query. Подписи граничных buckets используют серверные `from_at`/`to_at`, обрезанные по выбранному периоду. Неизвестный previous не участвует в вычислении отображаемого сравнения.

Миграции схемы БД управляются через Alembic с асинхронным режимом выполнения. Миграции используют `POSTGRES_LOCAL_DSN` из `.env` для подключения.

## Расширяемость

Новая доменная сущность добавляется вертикальным срезом: ORM-модель в `app/models/`, Pydantic-схемы в `app/schemas/`, CRUD-репозиторий в `app/crud/`, обработчики в `app/api/v1/` и при необходимости в `app/api/ext/v1/`.

Новая фоновая задача регистрируется через декоратор `@registry.job()` в соответствующей директории (`app/jobs/hourly/`, `app/jobs/daily/` и т.д.).

Новая интеграция с внешней системой добавляется как HTTP-клиент в `app/services/` по аналогии с MessageService.
