# Архитектура

`status: complete` обозначает полноту этого документа. Синхронизация проектных спецификаций одобрена пользователем 2026-10-12; операторский rollout и подтверждение production-условий остаются открытыми.

## Архитектурный стиль

Слоистая архитектура с разделением на API, CRUD-слой, модели и инфраструктуру.
Каждый слой имеет чёткую зону ответственности: API принимает запросы и валидирует входные данные, CRUD инкапсулирует доступ к базе данных, модели определяют структуру таблиц, сервисы координируют поперечные задачи.

Зависимости направлены внутрь: обработчики импортируют CRUD и сервисы, CRUD оперирует моделями через адаптер базы данных. Основная бизнес-логика находится в обработчиках API; read-only аналитика статистики реализована в StatsService.

## Основные компоненты или слои

- **API административное** (`app/api/v1/`) — REST-эндпоинты для управления пользователями, аккаунтами, сессиями, сообщениями, Android-устройствами, версиями, логами и опциями, а также read-only stats summary/live; защищённые маршруты используют JWT. Standalone `/api/v1/accounts/upload` и `/remove` сохраняют отсутствие обязательного JWT и аудит с `user_id=NULL`; маршрутизация выполняется через `api_router`
- **API внешнее** (`app/api/ext/v1/`) — интеграционные эндпоинты для загрузки/получения аккаунтов, управления сессиями (start/finish/ban), создания и обновления статусов сообщений, генерации HTML-отчётов; аутентификация через API Key
- **CRUD-слой** (`app/crud/`) — обобщённый репозиторий `CRUDBase` с поддержкой фильтрации через fastapi-filter, массовых операций (insert, map_update), upsert; конкретные репозитории для каждой доменной сущности
- **Модели** (`app/models/`) — SQLAlchemy ORM-модели: User, Account, Session, Message, Android, Log, Version; определения статусов через IntEnum
- **Схемы** (`app/schemas/`) — Pydantic-схемы для валидации входных данных и сериализации ответов; фильтры на базе fastapi-filter
- **Сервисы** (`app/services/`) — LogService для нормализации событий, account/file-аудита внешнего и административного API и общего независимого аудита ошибок start/finish/ban; MessageService — HTTP-клиент к внешнему Message API; StatsService — период, область доступа, log-only summary, независимый live и качество подсчёта сохранённой истории
- **Планировщик задач** (`app/jobs/`) — APScheduler с декоратором-реестром для регистрации задач; текущие задачи: освобождение неактивных аккаунтов и сессий
- **Адаптеры** (`app/adapters/`) — адаптер базы данных: создание async-движка, sessionmaker, базовый класс моделей
- **Инфраструктура** (`app/core/`) — конфигурация (5 групп настроек через pydantic-settings), логирование, безопасность (хеширование паролей, JWT), утилиты
- **Зависимости** (`app/deps.py`) — FastAPI-зависимости: get_db, get_current_user, get_user_by_api_key, get_basic_auth_user, as_form
- **HTML-дашборд** (`html/dashboard/`) — `DashboardApi` для stats/options и контроллер `dashboard.js` с независимыми каналами summary/live/users, двенадцатью историческими карточками и шестью графиками Kendo; четыре live-показателя отображаются отдельно
- **Общий frontend** (`html/static/auth.js`, `html/static/script.js`) — хранение и проверка token, общий header/Drawer и logout для административных страниц

## Границы ответственности

Обработчики API принимают HTTP-запрос, валидируют параметры через Pydantic-схемы, проверяют аутентификацию и авторизацию, вызывают CRUD-операции и сервисы, формируют ответ. На текущем этапе обработчики содержат значительную часть бизнес-логики: проверку уникальности, каскадные обновления, управление файлами.

CRUD-слой является основным слоем SQL-доступа к доменным данным. Базовый класс `CRUDBase` предоставляет типизированные методы get, list, count, create, insert, update, map_update, upsert, delete с поддержкой фильтрации и пагинации. Конкретные репозитории наследуют базовый класс и привязывают модель и класс фильтра. `UserCRUD.get_options` выбирает только публичные text/value; API назначает область member по User.id, а admin получает также неактивных пользователей. Подпись использует name, затем login, затем `Пользователь {id}`, сортировка выполняется по lower(label) и id.

`AccountCRUD.delete_returning_id` выполняет узкий `DELETE RETURNING` без commit, синхронизирует identity map и возвращает ID действительно удалённой строки либо `None`. Обработчик заранее сохраняет ответ и target-снимок, записывает `account.delete` в той же бизнес-транзакции и сам выполняет commit.

Сервисы реализуют поперечную функциональность, не привязанную к одному эндпоинту. LogService нормализует статусы и записывает события аудита. MessageService — HTTP-клиент к внешнему сервису сообщений.

`LogService` (`app/services/log.py`) централизует account/file-аудит обоих API и `session.error` внешних start/finish/ban. `operation(action, user_id, source)` создаёт отдельный dataclass `LogOperation` только со состоянием запроса: UUID, action, nullable actor, source, stage, db_outcome, код/выбор ошибки, доверенные/новые FK, очередь фактов и состояние освобождения транзакции. Методы `operation_context`, `queue_event`, `flush_events` и `report_error`, освобождение транзакции, независимая запись и диагностика принадлежат сервису. Сессионные callers сохраняют default `source=ext_api`; административные задают `source=api`. Прежний модуль `app/services/session_error.py` удалён. Upload использует тонкий callback к `LogService.upload_details`; сессионные вызовы не передают request-details.

`operation_context` отделяет разрешённые метаданные успеха от изменяемых объектов, не утверждая будущий исход commit. `queue_event` синхронно, без I/O и release, сохраняет immutable JSON-снимок identity/event/source/stage/error/details/target и `db_outcome` на момент наблюдения. Последующий commit не переписывает снимок и не повышает неподтверждённый FK до доверенного. `transaction_released` добавляется при финализации и относится к этому более позднему моменту. `event=None` обозначает только техническую диагностику, например профильную ошибку.

Во внешнем upload фактическая запись архива даёт независимый `account.file.upload` до профильного и бизнес-этапов. Ошибки проверки/записи архива дают `account.file.upload.error`, физическая ошибка удаления — `account.file.delete.error`; то же файловое исключение не дублируется общим `account.error`. Общие, SQL, response и audit-этапы остаются в `account.error`. Старый архив очищается после подтверждённого business commit и проверки ссылок; только выполненный unlink даёт `account.file.delete`, отсутствие при автоматической очистке является skip. Profile-only действия и ошибки не создают новых DB-событий; ранее наблюдённый архивный факт при этом сохраняется. `_set_account_hash` и оба hash-маршрута не переработаны: их успех остаётся `account.update`, как update-ветка upload и административный PUT без поля `status`. Наличие `status` в PUT выбирает `account.status` независимо от фактической смены значения (Q1).

Административные create/PUT сохраняют имена успешных событий и бизнес-транзакции. GET списка, одной записи, summary и missing-files получают error-only аудит после входа в обработчик; успешные чтения не пишут success-события и не делают commit ради журнала, временный PAUSED списка не фиксируется в БД. Ошибки зависимостей до входа в обработчик этим аудитом не охватываются. При одиночном и массовом удалении файловый I/O предшествует DB-delete, но факты архива буферизуются до release; нефатальный unlink-сбой не откатывает bulk. Каждая цель имеет отдельный снимок с ID/UUID/владельцем/статусом и при необходимости индексом входного списка, все факты запроса — один operation UUID. Повторные ID пропускаются до повторного I/O; отсутствующий single сохраняет 404, bulk — skip.

Standalone архивные `/api/v1/accounts/upload` и `/remove` сохраняют form/response-контракты без обязательного JWT (Q2). Их actor всегда `NULL`, в том числе при переданном непроверенном Authorization или клиентском user_id; он не выводится из имени файла или параметров. Явный remove сохраняет 404 и при исчезновении файла между exists/unlink. `/profile/upload` и `/profile/remove` остаются вне нового DB-аудита.

StatsService (`app/services/stats.py`) реализует `resolve_period` для UTC-интервала, календарного предела и сравнения, асинхронный `resolve_scope` для self/admin-all/admin-selected, а также `get_summary` и `get_live`. Выбранный администратором пользователь проверяется через существующий `UserCRUD.get`. Summary выполняет один read-only CTE SELECT только по `log`, объединяя оба периода, buckets, первые свидетельства сообщений/ошибок и audit gaps в одном snapshot. Вся историческая область задаётся `log.user_id` до агрегации/MIN; текущие доменные строки и владельцы в summary не участвуют. Live отдельно читает текущий пул `account` по текущему владельцу и фактическому `statement_timestamp()`. Для admin-all и scoped используются две фиксированные SQL-формы с bind-параметрами; ручных дат сбора нет. Log-only основа и actor scope уже существовали в baseline задачи account/file-аудита.

Success-метрики `accounts_uploaded`, `accounts_created`, `accounts_updated` считают точные события `account.file.upload`, `account.create`, `account.update` без дополнительных ограничений по source, FK, operation_id, action или версии context. Прежние записи с `context={}` учитываются. `closed` вычисляется в SQL как `finished + session_bans`, без повторного прибавления включённого в finished `auto_finished`; lifecycle FK/status-предикаты сохранены. Три account-error категории учитывают `api/ext_api`, `session.error` — только `ext_api`. Ошибки дедуплицируются по event/source/log.user_id/operation_id, включая NULL actor; первое свидетельство сообщений и ошибок ищется в сохранённой истории выбранной области до нижней границы периода. Legacy `account.error` не переклассифицируется по stage. Удаления аккаунтов и успешные удаления файлов отдельных счётчиков не добавляют.

Пользователь одобрил узкое исключение из правила размещения SQL в CRUD: только read-only аналитические SELECT внутри StatsService, без `FOR UPDATE`, commit, записывающих SQL и изменений ORM-сущностей. Реализованный поток: API stats → StatsService → существующий CRUD для scope / SQLAlchemy и адаптер БД для агрегатов. Отдельный пакет запросов, ORM-сущность и CRUD статистики не вводятся; исключение не распространяется на остальные сервисы.

Историческое состояние плана `plans/261003-dashboard-backend/plan.md`: код summary/live и маршруты фазы 3 готовы; фаза 4 завершена в коде и локальной верификации после одобренных пользователем исправлений общего auth/header и регрессионных проверок. Локальная приёмка явно одобренной фазы 5 выполнена, первые два пункта завершены. Третий пункт выполнен частично: локально проверены snapshot, основные сессионные операции и неизменность собственной тестовой схемы, но рабочие metadata и стоимость на согласованном репрезентативном объёме остаются открытыми. Последующее прямое поручение пользователя от 2026-10-05 реализовано как унификация аудита в LogService и удаление ручной coverage-конфигурации; прежнее требование подтверждать даты начала сбора отменено. Rollout и подтверждение работы аудита на всех обслуживающих workers остаются открытыми; `plans/261003-dashboard-backend/rollout.md` подготовлен, но не выполнен. Историческая общая реализация остаётся `in_progress`; её прежние cohort/ownership-контракты не описывают текущий summary.

Историческая локальная приёмка фазы 5 до унификации проверяла архитектуру без изменения runtime-кода. Независимые контрольные SQL сверяют метрики, периоды, buckets, cohort, доставляемость и live через реальные stats-маршруты на изолированной PostgreSQL. Тестовая advisory CTE оборачивает неизменённый service SELECT с сохранением типизированных bind-параметров и подтверждает единый snapshot через конкурентный commit для scoped/admin-all; следующий SELECT без обёртки видит новые данные в той же READ COMMITTED-транзакции. Отдельно прямые вызовы настоящих start на существующем аккаунте → finish → ban → ban выполняются одновременно с обычными stats-чтениями, сохраняя реальные CRUD, статусы, аудит и attempts. После унификации добавлены реальные upload-транзакции и повторена расширенная выборка регрессий. Каталоги сравниваются до/после только внутри собственной UUID-схемы; это не проверка production parity, HTTP/auth-конкурентности или нагрузочного SLA. Полные результаты и команды ведутся в плане, ограничения — в `constraints.md`.

Текущая совместная локальная приёмка зафиксирована в `plans/261011-account-file-audit-dashboard/phase5.md`: 1661 Python-проверка в 31 файле, 190 Node-тестов, 157 Chromium-сценариев и 244 wire samples (240 summary и 4 live), flake8 25 файлов и mypy пяти runtime-модулей с ограниченными flags. Это результаты завершённого прогона, не сумма фаз и не новая проверка при обновлении документации. Там же находятся канонические команды и ограничения; весь Python-репозиторий и полный legacy внешний `account.py` успешными не объявляются.

Новых миграций, индексов и зависимостей эта задача не вводит. Рабочая схема/retention, репрезентативный объём и стоимость, окружение/артефакт выпуска и отката, разрешение оператора и аудит на всех обслуживающих workers остаются открытыми. Одобрение локальной документации не завершает релиз.

Модели определяют структуру таблиц и отношения между сущностями. Схемы определяют контракт API-запросов и ответов. Инфраструктура предоставляет конфигурацию, логирование и инструменты безопасности.

### HTML-дашборд и общая авторизация

`DashboardApi` (`html/dashboard/js/api.js`) выполняет только фиксированные GET к `/api/v1/stats/summary`, `/api/v1/stats/live` и `/api/v1/options/user` через существующий `api_base_url`. Каждый запрос читает актуальный Bearer token через `getToken`, имеет timeout 20 секунд и отменяемый handle. Перед обработкой успеха и ошибки проверяются актуальность credentials и отмена; успешный ответ дополнительно сопоставляется с ожидаемой областью, а summary — также с запрошенным периодом. Явная проекция snake_case → camelCase требует все 17 метрик в totals/previous/trend и семь coverage-групп, сохраняет `null` и серверный `closed`; бизнес-агрегаты SQL на клиенте не воспроизводятся. Текущие DTO не содержат cohort, `message_created` и доставляемость; неполный прежний ответ 11/4 вызывает protocol error.

Двенадцать карточек показывают три account-success, баны аккаунтов, три account-error категории, открытые и завершённые сессии, ошибки сессий, отправки и доставки. Шесть графиков охватывают lifecycle, сообщения, account-errors, session-errors, загрузку/сохранение аккаунтов и баны аккаунтов/сессий. График сообщений сохраняет SENT/DELIVERED/UNDELIVERED/FAILED, их порядок, цвета, типы, tooltip и действие клика; `failed` остаётся метрикой API и серией, без отдельной карточки. Выполненные файловые действия и бизнес-записи не образуют воронку, сумма категорий ошибок не является количеством уникальных неуспешных запросов.

Фильтр событий журнала (`html/logs/js/grid.js`) содержит 19 вариантов: три прежние группы, девять прежних событий и семь добавленных вариантов `account.delete`, `account.error`, `account.file.upload`, `account.file.delete`, их две `.error` категории и `session.error`. Произвольная строка event остаётся допустимой для чтения/передачи в фильтр; source/status-фильтры и права logs API сохранены.

Интерфейс поясняет, что статистика рассчитана по сохранённым событиям: ноль означает отсутствие записанных событий, а не доказанное отсутствие прошлой активности. Предупреждения о качестве подсчёта и отображение `null` сохранены. Адаптер принимает прежнее ненулевое поле coverage `from` для совместимости, но UI не выводит его как гарантированную дату начала сбора.

`dashboard.js` управляет отдельными запросами и revision guards summary/live/users. Выбранный владелец обновляется до валидации периода и не зависит от успеха summary; при смене владельца прежние карточки, графики, live и диалог очищаются. Live обновляется каждые 60 секунд независимо от дат и не запускает второй таймерный запрос поверх pending-запроса. `pagehide` отменяет работу и отключает timers/observer; persisted `pageshow` возобновляет её один раз, включая незавершённую загрузку options даже при невалидном периоде.

`auth.js` сохраняет синхронные `getToken`/`setToken` и объект `window.isAuth` с четырьмя полями `access_token`, `token_type`, `ts`, `user`; поддерживаются фактический lowercase `bearer` и прежние timestamps без timezone. Некорректные данные storage безопасно очищаются. `setToken(null)` очищает cached/stored token и инвалидирует старую revision. Каждый `POST /api/v1/auth/test-token` использует свежий снимок storage; обе ветки ответа проверяют revision запроса и fingerprint token/type/user ID/role/active. Обновление только `ts` не считается новым входом. Для auth действует один таймер 60 секунд и timeout запроса 20 секунд.

Общий DOM-ready обработчик в `script.js` повторно читает token и проверяет его на `null`. Разметка Kendo header статична, имя добавляется через `.text()` с fallback name → login → `Пользователь {id}`; HTML и выражения Kendo в имени остаются текстом. Logout использует `setToken(null)`. Эти исправления не являются переработкой credential caches остальных legacy grids; backend авторизации в фазе 4 не менялся.

Ссылка на `/dashboard/` сейчас видима в меню admin и member через `dashboardNavigation`; прямой путь также работает. Прежнее описание `dashboardNavigation1=''` в версии `4956e7b` относится к историческому состоянию старого плана. Видимое меню, переходы на dashboard после входа, пользовательские auth/CSS/live-изменения уже существовали в baseline задачи account/file-аудита и не введены этой реализацией; гарантии shared auth/header сохранены.

## Поток запроса или выполнения

```
Запрос → FastAPI → Auth (JWT / API Key) → Обработчик → CRUD / Сервис → БД → Ответ
```

Типичный поток обработки запроса в административном API:

1. FastAPI маршрутизирует запрос к соответствующему обработчику
2. Dependency injection предоставляет асинхронную сессию БД через `get_db`
3. Зависимость `get_current_active_user` верифицирует JWT-токен и извлекает пользователя
4. Обработчик валидирует входные данные через Pydantic-схему
5. Обработчик применяет бизнес-логику: проверяет уникальность, права доступа, состояние сущностей
6. CRUD-репозиторий выполняет SQL-операции (create, update, delete, list)
7. LogService записывает событие аудита (при изменении статуса)
8. Транзакция коммитится, ответ сериализуется через Pydantic-схему

Поток внешнего API отличается аутентификацией (API Key через `get_user_by_api_key`) и бизнес-логикой: эндпоинты ориентированы на интеграцию — атомарное получение аккаунта с блокировкой, создание сообщений, обновление статусов сессий.

Для stats `api_router` регистрирует `GET /api/v1/stats/summary` и `/live`. После `get_current_active_user` и валидации query DTO обработчик вызывает StatsService и сериализует результат без commit. Один аналитический statement на агрегат не исключает отдельных SELECT аутентификации и проверки выбранного владельца.

Обычный клиентский поток: `dashboard.js` → `DashboardApi` → JWT stats/options → DTO → карточки/графики/live. Только явный `?demo=1` загружает `mock_data.js` и выбирает `DashboardMock`, без запросов stats/options; общая авторизация продолжает работать. Ошибки API не переключают источник данных на mock.

Внешние системы доступны через HTTP-клиент в `app/services/message/client.py`. Клиент инкапсулирует взаимодействие с Message API (campaigner.o3go.ru): получение следующего сообщения и обновление статуса.

На текущем этапе адаптеры внешних систем не вынесены в отдельный слой — HTTP-клиент находится в сервисном слое. Адаптер базы данных в `app/adapters/db/` предоставляет async-движок и sessionmaker.

## Стратегия обработки ошибок

Ошибки обрабатываются на уровне обработчиков API: бизнес-логика возвращает HTTPException с соответствующим кодом статуса (400, 401, 403, 404, 409, 422).

StatsService выдаёт типизированные ошибки `StatsPeriodError`, `StatsScopeDeniedError` и `StatsUserNotFoundError`, которые stats API отображает в HTTP 422, 403 и 404. Зарегистрированные маршруты проверены отдельно от contract-probes фазы 1; сохранены штатные auth-отказы: отсутствие токена — 401, невалидный JWT — 403, неактивный пользователь — 400.

Локальный `_StatsRoute` в `app/api/v1/stats.py` перехватывает `SQLAlchemyError`, включая ошибки auth-зависимостей и проверки выбранного владельца, и возвращает общий 503 без SQL и приватных деталей. Это не глобальный middleware; обработка других маршрутов не менялась. Диагностика через `asyncio.to_thread` передаёт logger только action и тип ошибки без сообщения/traceback, затем независимо пишет в stderr, даже если handler logger подавил I/O-ошибку. Отказы каналов, включая одновременный отказ обоих, оставляют безопасные notes в HTTPException и сохраняют ответ 503.

Дашборд показывает отдельные loading/error/unavailable состояния каналов и фиксированные безопасные сообщения вместо текста серверного ответа. Последний корректный snapshot той же области при временном сбое явно помечается как прежний; `null` при невозможности надёжно посчитать error-группу отображается как «—» и пропуски графика, а не нули. Временные сбои summary/live изолированы; отказ авторизации или несоответствие сеанса/scope останавливают каналы и очищают отображаемые данные.

Для общей проверки входа актуальные 401/403/404, 400 с `detail: "Inactive user"` либо корректный профиль с `is_active: false` очищают auth и ведут на `/auth/`. Сеть, timeout, 5xx и некорректный ответ сохраняют действующий token, выдают фиксированное безопасное предупреждение и оставляют повторную проверку по таймеру. Устаревшие ответы не могут восстановить старый вход или удалить новый token.

Внешние upload/start/finish/ban и охваченные административные account/archive-обработчики перехватывают `Exception` и `asyncio.CancelledError` и вызывают `LogService.report_error(db, error, operation=..., details=...)`. Общий корень контекста ошибки содержит `operation_id`, `action`, nullable `user_id`, `stage`, `db_outcome`, `error` и сведения об освобождении транзакции; event/source задаются отдельно в записи журнала. Общая диагностика исключает исходные сообщения исключений, SQL/параметры и произвольные OS paths; сохраняет тип, безопасный код, HTTP status, SQLSTATE/errno и имена объектов БД. Диагностические строки ограничены 160 символами, обход причин — 12 исключениями, traceback — 12 координатами с basename файла, функцией и строкой, без locals.

Сессионный аудит не копирует request-details, device/API/auth-данные или `info_*`. Upload отдельно помещает в `details` разрешённые метаданные запроса, файлов и снимков аккаунта: в том числе `number`, `type`, `limit`, `cooldown`, `geo`, `info_1..info_8`, имя/тип/размер файла, ветку, storage/cleanup и признак наличия hash. Значения hash, headers, содержимое файлов и произвольные поля запроса не копируются; разрешённые upload-метаданные могут содержать пути хранения. Административные callers передают allowlist target/file-метаданных, `operation_context` дополнительно исключает известные приватные ключи. Это отдельный контракт от очищенной общей диагностики исключения. Actor фиксируется скалярно до первого I/O либо остаётся NULL для standalone архивов. Внешние операции доверяют существующим FK после проверки владельца; новый FK независимого аудита допустим только после подтверждённого commit. Очередь принимает account FK явно и не наследует его из изменяемого состояния при flush.

`LogService.flush_events` и `report_error` возвращают bool подтверждённого освобождения бизнес-транзакции, а не успешности записи аудита. Finalizer защищён через `asyncio.shield`: весь буфер обрабатывается до очистки зависимостей и передачи внешней отмены, включая повторные отмены; первичная ошибка сохраняется. Обычный отказ одного writer не теряет следующие факты; неизвестный исход audit commit потребляется один раз без retry. Неподтверждённое освобождение включает latch, блокирующий последующие writers операции; оставшиеся неподтверждённые факты получают fallback. Минимальный stderr fallback обязателен независимо от logger, в том числе при неожиданном отказе finalizer/защищённой задачи и после commit, когда upload может вернуть HTTP 201. Отказ stderr отмечается безопасной note в исходном исключении. Намеренное исключение profile-only записи через `persist_error=False` или `event=None` не считается `audit_unavailable`; отказ её технической диагностики имеет отдельный `diagnostics_unavailable` fallback.

В общей технической диагностике LogService не-HTTP ошибки относятся к `E.SYSTEM.API.ERROR`, HTTP 404 — к `NOT_FOUND`, остальные 4xx — к `FAILURE`. Это классификация унифицированных операций; обработка auth/message и legacy-логирование других account-маршрутов ею не переопределяются. Обычные ошибки cleanup и success logger после подтверждённого upload commit сохраняют HTTP 201; отмена передаётся вызывающему коду. Несколько ошибок одного запроса используют один UUID операции. Бизнес-commit, переходы статусов, lifecycle-аудит и attempts, включая повторный ban, сохраняют прежнюю семантику.

Внешний HTTP-клиент (MessageService) обрабатывает сетевые ошибки: HTTPStatusError, TimeoutException — логирует и возвращает None, не прерывая выполнение.

## Управление данными и состоянием

Основное хранилище — PostgreSQL 12. Все операции с данными проходят через асинхронные сессии SQLAlchemy, создаваемые на уровне запроса через dependency injection либо отдельно для независимого аудита.

Каждый запрос получает собственную сессию. Для изменяющих операций коммит транзакции управляется обработчиком: операции выполняются с `commit=False`, а коммит вызывается явно после всех изменений (CRUD + LogService). StatsService выполняет только чтение и не вызывает commit.

В охваченных операциях исход бизнес-транзакции начинается с `not_committed`, становится `unknown` перед ожиданием business commit и `committed` только после его успешного возврата. LogService сначала выполняет rollback, при необходимости close и проверяет отсутствие активной транзакции; при неподтверждённом освобождении независимый writer не запускается и не повторяется. После освобождения существующий `LogService.record_independent` записывает событие через CRUD в собственной сессии с собственным commit. При неизвестном исходе новые FK остаются NULL даже при фактическом сохранении бизнес-строк; доверенные существующие FK допустимы. Файловый факт admin-delete, наблюдённый до commit, сохраняет `db_outcome=not_committed` даже при последующем успешном удалении и `transaction_released=true`. StatsService в этом пути не участвует.

`account.delete` атомарен с DB-delete и записывается с `account_id/session_id/message_id=NULL`, сохраняя target в context. Файловые факты одиночного/bulk удаления также имеют NULL доменные FK и независимую запись после release, поэтому удаление аккаунта их не каскадирует. Прежние CASCADE/retention не менялись; это не гарантия сохранности старых связанных логов. Новый аудит остаётся best-effort с очередью в памяти, без outbox, crash-durability и обещания exactly-once. Member logs API по-прежнему ограничивает строки через текущего владельца связанного account: NULL-FK событие ему не видно в журнале, хотя оно может учитываться в actor-summary. Anonymous-события с NULL `log.user_id` входят только в admin-all, а не в персональные области.

`STATS_COVERAGE_STARTS`, связанные типы/валидатор settings и пример переменной в `.env.example` удалены; `get_summary` больше не принимает `coverage_starts`. Общий RFC 3339 тип `app/core/utc.py` сохранён для UTC-контрактов DTO. Статистика по умолчанию возвращает численные значения сохранённой истории, включая нули при отсутствии записанных событий. Настройка даты сбора, фиктивные даты и backfill для этого не используются.

Wire-контракт totals/previous/каждого trend bucket содержит 17 обязательных nullable-метрик. Семь групп `coverage` — `lifecycle`, `message_events`, `account_errors`, `session_errors`, `account_events`, `account_file_upload_errors`, `account_file_delete_errors` — всегда получают `from: null`. `recorded` означает возможность подсчитать сохранённые записи, а не полноту сбора. Единственная текущая причина `partial` — `missing_operation_id`: отсутствующий, JSON null или пустой operation_id маскирует только соответствующую одну из четырёх error-групп целиком для затронутого current/previous периода и всех его buckets. Source-предикаты счётчиков и gaps совпадают; недопустимый source не создаёт ложного gap, другие группы и другой период не маскируются. Даты сбора, backfill, cohort, `message_created` и доставляемость в текущем stats-контракте отсутствуют; независимый live, SQL/global-first, scope и правила периода сохранены. Пустой диапазон даёт нули и пустой ряд.

Ручной ввод дат дашборда интерпретируется как UTC, включая часы внутри локального DST gap браузера. Клиент проверяет календарный предел месяца с ограничением дня последним днём следующего месяца; открытый конец не передаётся в query. Подписи граничных buckets используют серверные `from_at`/`to_at`, обрезанные по выбранному периоду. Неизвестный previous не участвует в вычислении отображаемого сравнения.

Миграции схемы БД управляются через Alembic с асинхронным режимом выполнения. Миграции используют `POSTGRES_LOCAL_DSN` из `.env` для подключения.

## Расширяемость

Новая доменная сущность добавляется вертикальным срезом: ORM-модель в `app/models/`, Pydantic-схемы в `app/schemas/`, CRUD-репозиторий в `app/crud/`, обработчики в `app/api/v1/` и при необходимости в `app/api/ext/v1/`.

Новая фоновая задача регистрируется через декоратор `@registry.job()` в соответствующей директории (`app/jobs/hourly/`, `app/jobs/daily/` и т.д.).

Новая интеграция с внешней системой добавляется как HTTP-клиент в `app/services/` по аналогии с MessageService.
