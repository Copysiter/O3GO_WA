# Обзор проекта

`status: complete` обозначает полноту документации, а не завершённый релиз. Синхронизация спецификаций одобрена пользователем 2026-10-12; операторские условия rollout остаются открытыми.

## Описание

O3GO WA — система управления WhatsApp-аккаунтами для массового рассылочного трафика.
Сервис предоставляет два API: административное для управления пользователями, аккаунтами, сессиями и сообщениями через веб-интерфейс, и внешнее интеграционное для подключения Android-приложений и сторонних систем.

Система отслеживает жизненный цикл WhatsApp-аккаунтов: загрузка архивов, создание и завершение сессий, отправка сообщений, баны и кулдауны. Встроенный планировщик автоматически освобождает неактивные аккаунты и сессии.

---

## Назначение

Сервис решает задачу централизованного управления парком WhatsApp-аккаунтов с разграничением доступа между администраторами и внешними потребителями.
Администраторы управляют пользователями, аккаунтами и мониторингом через защищённое REST API. Внешние системы интегрируются через API Key для получения аккаунтов, отправки сообщений и управления статусами сессий.

Встроенная система аудита фиксирует все изменения статусов, что позволяет отслеживать историю операций и диагностировать проблемы.

---

## Системный контекст

Сервис работает как самостоятельный компонент платформы O3GO и взаимодействует с PostgreSQL для хранения данных и внешним Message API (campaigner.o3go.ru) для получения и обновления статусов сообщений.

Потребителями административного API являются администраторы системы. Внешним API пользуются Android-приложения, работающие на физических устройствах, и другие внешние системы рассылки.

## Архитектурный стиль

Слоистая архитектура с разделением на API, CRUD-слой, модели, схемы, сервисы и адаптеры.
Зависимости направлены внутрь: обработчики API используют CRUD-операции и сервисы, CRUD оперирует ORM-моделями через адаптер базы данных.
Сервисный слой содержит LogService с account/file-аудитом внешнего и административного API и аудитом ошибок start/finish/ban, внешний HTTP-клиент и read-only аналитику stats: период, область доступа, агрегаты и качество подсчёта сохранённой истории. Основная бизнес-логика находится в обработчиках API. По одобренному пользователем исключению аналитические SELECT размещены только внутри StatsService без мутаций и commit; summary читает журнал по вызывающему пользователю, live — текущее состояние по владельцу аккаунта.

## Ключевые технологии

- Python 3.11 — runtime с поддержкой async/await
- FastAPI — HTTP-фреймворк, dependency injection, автогенерация OpenAPI-документации
- SQLAlchemy 2.0 (async) — ORM, асинхронные сессии через asyncpg
- Pydantic 2 — валидация данных, Pydantic-схемы запросов и ответов, конфигурация через BaseSettings
- PostgreSQL 12 — основное хранилище доменных данных
- Alembic — управление миграциями БД
- python-jose — генерация и верификация JWT-токенов (HS256)
- APScheduler — планировщик фоновых задач
- httpx — асинхронный HTTP-клиент для внешнего Message API
- pytest + pytest-asyncio — тестирование
- Uvicorn — ASGI-сервер
- Docker + Docker Compose — контейнеризация и локальная разработка
- JavaScript, jQuery 1.12.4 и Kendo UI 2022.2.510 — существующий статический административный интерфейс и дашборд

## Основные компоненты

- **API административное** (`app/api/v1/`) — REST-эндпоинты для управления пользователями, аккаунтами, сессиями, сообщениями, Android-устройствами, версиями, логами и чтения статистики summary/live; защищённые маршруты используют JWT. Standalone архивные `/api/v1/accounts/upload` и `/remove` сохраняют отсутствие обязательного JWT и записывают новый аудит с неизвестным actor (`user_id=NULL`).
- **API внешнее** (`app/api/ext/v1/`) — интеграционные эндпоинты для загрузки/получения аккаунтов, управления сессиями и сообщениями, генерации отчётов; аутентификация через API Key
- **CRUD-слой** (`app/crud/`) — обобщённый репозиторий `CRUDBase` с поддержкой фильтрации, массовых операций и upsert; узкий `AccountCRUD.delete_returning_id` подтверждает удаление для общей транзакции с `account.delete`.
- **Сервисы** (`app/services/`) — LogService (`app/services/log.py`) для бизнес-событий, независимых account/file/session ошибок и накопленных неизменяемых файловых фактов после освобождения транзакции; MessageService — HTTP-клиент к внешнему Message API; StatsService (`app/services/stats.py`) — read-only summary/live, 17 счётчиков и семь групп качества сохранённой истории.
- **Планировщик задач** (`app/jobs/`) — фоновые задачи: освобождение неактивных аккаунтов и сессий старше 24 часов
- **Инфраструктура** (`app/core/`) — конфигурация через pydantic-settings, логирование, безопасность (хеширование паролей, JWT), утилиты
- **HTML-дашборд** (`html/dashboard/`) — 12 исторических карточек, шесть графиков и независимый live-срез; `DashboardApi` подключает stats/options, а `DashboardMock` доступен только при `?demo=1`. График сообщений сохраняет четыре серии, включая failed без отдельной карточки; фильтр журнала содержит 19 вариантов event.
- **Общий frontend** (`html/static/auth.js`, `html/static/script.js`) — синхронные token helpers, периодическая проверка входа с защитой от устаревших ответов, навигация, безопасный текстовый вывод имени в header и logout

## Важные замечания для разработки

### Текущая реализация и приёмка

- `plans/261011-account-file-audit-dashboard/plan.md` фиксирует реализованный account/file-аудит двух API, расширенные stats и UI. Код, совместная локальная приёмка и одобренная синхронизация документации выполнены; операторский пункт остаётся открытым. Фактического deployment нет.
- Бизнес-события `account.create/update/status/delete` и архивные `account.file.upload/delete` с их `.error` различаются. Файловая ошибка не дублируется общим `account.error`, profile-only действия и их ошибки не создают новых DB-событий. Сохраняются account.update upload/admin/hash и прежний выбор status в PUT. Удаление аккаунта и `account.delete` атомарны; новые delete/file-факты с NULL доменными FK и target-снимком не теряются при CASCADE, но старый retention/CASCADE не меняется.
- LogService хранит неизменяемые факты запроса и защищённо записывает их после подтверждённого release; bool финализаторов означает освобождение транзакции, не успех аудита. Сохраняются cancellation, первичная ошибка, fallback и обычный post-commit HTTP 201 upload. Best-effort очередь в памяти не обещает полной crash-durability или exactly-once.
- Summary остаётся log-only по `log.user_id`; anonymous события учитываются только в admin-all, live — по текущему владельцу. DTO содержит 17 метрик и семь coverage-групп с `from: null`. `closed = finished + session_bans`, без повторного auto_finished. Только `missing_operation_id` маскирует соответствующую одну из четырёх error-групп затронутого периода и его buckets. Ноль означает отсутствие записанных событий; ручных дат, backfill, текущих cohort/delivery полей нет.
- DashboardApi требует контракт 17/7, сохраняет NULL и независимые каналы summary/live/users. UI показывает 12 карточек и шесть графиков, не пересчитывает SQL-агрегаты; график сообщений, auth/header и archive widget не переработаны. Ссылка на дашборд видима для admin/member. Log-only основа, видимая навигация и пользовательские auth/CSS/live-изменения уже были в baseline задачи.
- Совместная приёмка в `plans/261011-account-file-audit-dashboard/phase5.md`: **1661 Python** в 31 файле, **190 Node**, **157 Chromium-сценариев**, **244 wire samples** (240 summary и 4 live). Целевые flake8 25 файлов и ограниченный mypy пяти runtime-модулей прошли; весь Python-репозиторий и полный legacy ext/account.py успешными не объявляются. Тестовый PG12-контейнер удалён; при этой синхронизации документации приложение и тесты заново не запускались.
- Новый `plans/261011-account-file-audit-dashboard/rollout.md` подготовлен, но не выполнен: backend раньше нового UI, при откате совместимый UI раньше backend с учётом кеша и открытых вкладок. Production metadata/retention, согласованная стоимость, окружение/релиз/откат и работа аудита всех обслуживающих workers остаются открытыми. Одобрение документации не разрешает rollout.

### Общие эксплуатационные сведения

- Внешнее API использует API Key (заголовок `X-Api-Key` или query-параметр `x_api_key`), защищённые административные маршруты — JWT. Отдельное исключение standalone архивов описано выше; их actor нельзя выводить из непроверенных credentials.
- Файлы аккаунтов (архивы .tar.gz и профили .txt) хранятся на файловой системе в директории `upload/wa/`
- Все изменения статусов аккаунтов, сессий и сообщений логируются через LogService в таблицу `log` с JSONB-контекстом
- Планировщик APScheduler запускает задачи по расписанию: освобождение аккаунтов в 0 минут каждого часа, сессий — в 5 минут
- Конфигурация загружается из `.env` через pydantic-settings, объединённый класс `GeneralSettings` наследует 5 групп настроек
