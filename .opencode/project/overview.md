# Обзор проекта

## Описание

O3GO WA — система управления WhatsApp-аккаунтами для массового рассылочного трафика.
Сервис предоставляет два API: административное для управления пользователями, аккаунтами, сессиями и сообщениями через веб-интерфейс, и внешнее интеграционное для подключения Android-приложений и сторонних систем.

Система отслеживает жизненный цикл WhatsApp-аккаунтов: загрузка архивов, создание и завершение сессий, отправка сообщений, баны и кулдауны. Встроенный планировщик автоматически освобождает неактивные аккаунты и сессии.

---

## Назначение

Сервис решает задачу централизованного управления парком WhatsApp-аккаунтов с разграничением доступа между администраторами и внешними потребителями.
Администраторы управляют пользователями, аккаунтами и мониторингом через защищённое REST API. Внешние системы интегрируются через API Key для получения аккаунтов, отправки сообщений и управления статусами сессий.

Встроенная система аудита фиксирует все изменения статусов, что позволяет отслеживать историю операций и диагностировать проблемы.

---

## Системный контекст

Сервис работает как самостоятельный компонент платформы O3GO и взаимодействует с PostgreSQL для хранения данных и внешним Message API (campaigner.o3go.ru) для получения и обновления статусов сообщений.

Потребителями административного API являются администраторы системы. Внешним API пользуются Android-приложения, работающие на физических устройствах, и другие внешние системы рассылки.

Backend API сервис (REST).

## Архитектурный стиль

Слоистая архитектура с разделением на API, CRUD-слой, модели, схемы, сервисы и адаптеры.
Зависимости направлены внутрь: обработчики API используют CRUD-операции и сервисы, CRUD оперирует ORM-моделями через адаптер базы данных.
Существующий сервисный слой содержит LogService с общим независимым аудитом ошибок upload/start/finish/ban, внешний HTTP-клиент и read-only аналитику stats: период, область доступа, агрегаты и качество подсчёта сохранённой истории; основная бизнес-логика на текущем этапе находится в обработчиках API. По одобренному пользователем исключению аналитические SELECT размещены только внутри StatsService без мутаций и commit.

## Ключевые технологии

- Python 3.11 — runtime с поддержкой async/await
- FastAPI — HTTP-фреймворк, dependency injection, автогенерация OpenAPI-документации
- SQLAlchemy 2.0 (async) — ORM, асинхронные сессии через asyncpg
- Pydantic 2 — валидация данных, Pydantic-схемы запросов и ответов, конфигурация через BaseSettings
- PostgreSQL 12 — основное хранилище доменных данных
- Alembic — управление миграциями БД
- python-jose — генерация и верификация JWT-токенов (HS256)
- APScheduler — планировщик фоновых задач
- httpx — асинхронный HTTP-клиент для внешнего Message API
- pytest + pytest-asyncio — тестирование
- Uvicorn — ASGI-сервер
- Docker + Docker Compose — контейнеризация и локальная разработка
- JavaScript, jQuery 1.12.4 и Kendo UI 2022.2.510 — существующий статический административный интерфейс и дашборд

## Основные компоненты

- **API административное** (`app/api/v1/`) — REST-эндпоинты для управления пользователями, аккаунтами, сессиями, сообщениями, Android-устройствами, версиями, логами и чтения статистики summary/live; аутентификация через JWT
- **API внешнее** (`app/api/ext/v1/`) — интеграционные эндпоинты для загрузки/получения аккаунтов, управления сессиями и сообщениями, генерации отчётов; аутентификация через API Key
- **CRUD-слой** (`app/crud/`) — обобщённый репозиторий `CRUDBase` с поддержкой фильтрации через fastapi-filter, массовых операций, upsert; конкретные репозитории по доменным сущностям
- **Сервисы** (`app/services/`) — LogService (`app/services/log.py`) для событий и независимого аудита account.error/session.error операций upload/start/finish/ban, MessageService — HTTP-клиент к внешнему Message API, StatsService (`app/services/stats.py`) — период, область доступа, read-only summary/live по сохранённым данным и NULL-маскирование error-групп без operation_id
- **Планировщик задач** (`app/jobs/`) — фоновые задачи: освобождение неактивных аккаунтов и сессий старше 24 часов
- **Инфраструктура** (`app/core/`) — конфигурация через pydantic-settings, логирование, безопасность (хеширование паролей, JWT), утилиты
- **HTML-дашборд** (`html/dashboard/`) — восемь карточек, шесть графиков и независимый live-срез; `DashboardApi` подключает stats/options, а `DashboardMock` доступен только в явном режиме `?demo=1`
- **Общий frontend** (`html/static/auth.js`, `html/static/script.js`) — синхронные token helpers, периодическая проверка входа с защитой от устаревших ответов, навигация, безопасный текстовый вывод имени в header и logout

- Пользователь ответом «да» одобрил переход к фазе 3 плана `plans/261003-dashboard-backend/plan.md`. Исторические успешные pytest и итоговые flake8/mypy фазы 3 на изолированной PostgreSQL 12 сохранены в плане; при завершении frontend фазы 4 Python-проверки заново не запускались. Фаза 1 завершена по уточнённому объёму, а перенесённая проверка рабочей БД остаётся первым открытым пунктом фазы 3; полное завершение фазы 3 не заявляется.
- По прямому поручению пользователя от 2026-10-05 аудит ошибок upload/start/finish/ban унифицирован в LogService. Отдельный `app/services/session_error.py` удалён; dataclass LogOperation содержит только состояние запроса, методы аудита принадлежат сервису. Независимый writer запускается после подтверждённого освобождения бизнес-транзакции, защищённое завершение сохраняет первичную ошибку/внешнюю отмену и обязательный stderr fallback. UUID общий для нескольких ошибок операции; обычные post-commit ошибки upload сохраняют HTTP 201. Бизнес-переходы, attempts и legacy-логирование остальных account-эндпоинтов сохранены.
- `STATS_COVERAGE_STARTS`, её типы/валидатор и пример в `.env.example` удалены; `get_summary` больше не принимает `coverage_starts`. Метрики численные по сохранённой истории, ноль означает отсутствие записанных событий. Четыре группы wire `coverage` сохранены с `from: null`; `recorded` означает возможность подсчёта, а не полноту сбора. Только `missing_operation_id` даёт `partial` и NULL всей соответствующей error-группы затронутого периода/всех buckets. UTC, календарный месяц, SQL/global-first, scopes, cohort и live сохранены. Прежний операторский барьер ручного подтверждения дат сбора отменён, фиктивные даты не вводятся.
- Фаза 4 завершена в коде и локальной верификации после одобренных исправлений общего auth/header. `DashboardApi` выполняет GET summary/live/options со свежим Bearer token; контроллер независимо управляет каналами, периодом UTC и владельцем, обновляет live каждые 60 секунд и сохраняет quality-warning/`null`. UI поясняет семантику сохранённой истории и не показывает legacy `coverage.from` как гарантированную дату сбора. Демо действует только при `?demo=1` с общей авторизацией. В пользовательском `html/static/script.js` ссылка на дашборд скрыта через `dashboardNavigation1=''`; прямой `/dashboard/` работает, shared script в этой унификации не менялся.
- Историческая приёмка фазы 5 до унификации включала независимые контрольные SQL, конкурентные транзакции и регрессии без изменения runtime-кода; её результаты сохранены. После унификации основной исполнитель повторил расширенную выборку 25 Python-файлов: 991 проверка прошла, включая шесть новых реальных PostgreSQL upload-сценариев. Также прошли 161 Node-тест, 116 browser-сценариев и новая валидация 144 wire samples действующими DTO. Целевые flake8/mypy успешны в ограниченном наборе; прежние 34 flake8 и два mypy замечания всего legacy `account.py` сохраняются. Это не проверка всего Python-репозитория; канонические команды и количества ведутся в плане.

Открыты read-only metadata/retention, согласованный релиз/откат/окружение и подтверждение аудита на всех обслуживающих workers. Ручные даты coverage больше не являются условием включения.
- Внешнее API использует аутентификацию по API Key (заголовок `X-Api-Key` или query-параметр `x_api_key`), административное — по JWT
- Файлы аккаунтов (архивы .tar.gz и профили .txt) хранятся на файловой системе в директории `upload/wa/`
- Все изменения статусов аккаунтов, сессий и сообщений логируются через LogService в таблицу `log` с JSONB-контекстом
- Планировщик APScheduler запускает задачи по расписанию: освобождение аккаунтов в 0 минут каждого часа, сессий — в 5 минут
- Конфигурация загружается из `.env` через pydantic-settings, объединённый класс `GeneralSettings` наследует 5 групп настроек
