# Ограничения проекта

## Технические ограничения

- Runtime — Python 3.11, совместимость с более ранними версиями не поддерживается
- Все I/O операции должны быть асинхронными (async/await), синхронные блокирующие вызовы запрещены в обработчиках запросов
- PostgreSQL является единственным поддерживаемым основным хранилищем, замена на другую СУБД не предусмотрена
- Файлы аккаунтов хранятся на локальной файловой системе (`upload/wa/`), что ограничивает горизонтальное масштабирование без внешнего object storage

## Архитектурные ограничения

- Зависимости между слоями направлены внутрь: обработчик → CRUD/сервис → модель → адаптер БД. Обратные зависимости запрещены.
- Доступ к базе данных осуществляется преимущественно через CRUD-слой. Сохраняется исключение для сложной логики с блокировками (FOR UPDATE SKIP LOCKED во внешнем API); пользователь также одобрил узкое исключение только для read-only аналитических SELECT внутри `StatsService` (`app/services/stats.py`).
- Для stats согласованы зависимости API → StatsService → существующий CRUD пользователя для scope / SQLAlchemy и адаптер БД для агрегатов. Отдельный пакет запросов и CRUD статистики не создаются. StatsService не допускает мутаций, записывающих SQL, `FOR UPDATE` и commit; исключение для аналитики не распространяется на остальные сервисы.
- Основная бизнес-логика на текущем этапе находится в обработчиках API. StatsService реализует период, область доступа, summary/live и coverage; stats API зарегистрирован через api_router. Каждый агрегат читается одним CTE SELECT, значения связаны параметрами, SQL-формы scoped/admin-all выбираются сервером. Массовое выделение остальной бизнес-логики в сервисы остаётся отдельной задачей рефакторинга.
- Для изменяющих операций коммит транзакции управляется обработчиком: CRUD-операции вызываются с `commit=False`, коммит — явно в обработчике.
- Общий аудит `account.error` для upload и `session.error` для start/finish/ban реализован только в `LogService`; `app/services/session_error.py` удалён. `LogOperation` — dataclass состояния отдельного запроса, без методов аудита. `report_error` освобождает бизнес-транзакцию, затем использует существующий `record_independent` с CRUD, собственной сессией и commit; прямого SQL в аудите нет. Его bool означает освобождение транзакции, а не успешность аудита. При неподтверждённом освобождении latch блокирует последующие независимые writers операции. Новые FK разрешены только после подтверждённого commit, чужие ссылки исключены; StatsService остаётся read-only.
- Защищённое завершение аудита сохраняет первичную ошибку и внешнюю отмену до очистки зависимостей. Минимальный stderr fallback обязателен при неподтверждённом аудите, включая неожиданный отказ finalizer/защищённой задачи и обычную post-commit ошибку upload с ответом 201; отказ stderr отмечается в исходном исключении. Общая диагностика ограничивает строки 160 символами, обход причин и traceback — 12 элементами, исключает raw exception messages, SQL/параметры и произвольные OS paths. Upload помещает разрешённые метаданные, включая `number`, `info_1..info_8` и storage/cleanup, только в `details`; hash-значения, headers и содержимое файлов исключены. Сессионный аудит не передаёт request-details.
- `STATS_COVERAGE_STARTS`, её типы/валидатор и пример `.env.example` удалены; `get_summary` не принимает `coverage_starts`. Сохранённые данные дают числа, отсутствие записанных событий — ноль. Четыре wire-группы coverage сохранены с `from: null`; `recorded` означает подсчитываемость, а не полноту сбора. Только `missing_operation_id` даёт `partial` и маскирует соответствующую error-группу всего затронутого current/previous периода и всех его buckets. Ручные даты, прежние причины по датам сбора и фиктивный backfill не используются; SQL/global-first, UTC/месяц, scopes, cohort и live сохранены.
- SQLAlchemyError статистики обрабатывается локальным _StatsRoute, включая auth-зависимости, с общим 503 и безопасной диагностикой вне event loop. Глобальный middleware и обработка остальных маршрутов не менялись. Общий UTCDateTime сохранён в core для DTO и проверки UTC-контрактов без обратного импорта верхних слоёв; удаление coverage-settings не удаляет этот тип.
- Дашборд получает бизнес-агрегаты через `DashboardApi` и фиксированные GET stats/options; клиент не воспроизводит SQL-расчёты, сохраняет `null` и отдельную семантику cohort. Явный `?demo=1` выбирает mock без stats/options-трафика, но с общей авторизацией; ошибки API не разрешают неявный fallback на вымышленные данные.
- UI объясняет семантику сохранённой истории и нулей, сохраняет quality-warning/`null` и не показывает принятый адаптером legacy `coverage.from` как гарантированную дату сбора. Пользовательская версия общего `script.js` скрывает ссылку через `dashboardNavigation1=''`; прямой `/dashboard/` доступен. Browser-ожидание соответствует скрытой ссылке; унификация не меняла shared script.

## Инфраструктурные ограничения

- Сервис запускается в Docker-контейнере на базе python:3.11
- Секреты передаются через переменные окружения, не хранятся в коде или Docker-образе
- Nginx обслуживает статические файлы из `html/`; в текущем `services/nginx.conf` нет действующего API proxy. Адрес API выбирает общий frontend, фактическая production-маршрутизация требует операторских сведений.
- Планировщик APScheduler работает в том же процессе, что и API-сервер — при масштабировании на несколько worker'ов задачи будут дублироваться
- Проверки stats и общего account.error/session.error-аудита используют отдельную PostgreSQL 12 с явными `STATS_TEST_POSTGRES_DSN` и `STATS_TEST_ALLOW_SCHEMA_CREATE=1`. До DDL fixtures проверяют адрес `127.0.0.1` с портом, отличным от 5432, выделенные БД `o3go_stats_test` и пользователя `stats_test`, PostgreSQL 12, пустую `public` и отсутствие других пользовательских схем.
- В `tests/integration/conftest.py` существуют два режима изоляции: внешняя транзакция с rollback для stats и фиксируемая схема `stats_test_<uuid>` для реальных независимых соединений и commit. Второй режим после повторных проверок защиты удаляет через `DROP SCHEMA ... CASCADE` только созданную тестом UUID-схему; рабочая БД и `public` не удаляются. Оба режима и conftest на фазе 3 не менялись; ANALYZE перед EXPLAIN выполнялся только на тестовых таблицах, а сами агрегаты дополнительно проверены в `SET TRANSACTION READ ONLY` без commit.
- Тестовая PostgreSQL не подтверждает схему, индексы, объёмы, retention и доступную историю рабочей БД. Пользователь подтвердил завершение фазы 1 по уточнённому объёму и перенос этой проверки в фазу 3: нужен явно предоставленный read-only endpoint либо операторский вывод. Проверки выполнялись с `env -i` из разрешённого временного CWD, без чтения рабочей `.env`, с фиктивным DSN приложения на порту 1; production-конфигурация не менялась.
- Историческая кодовая часть фазы 2 реализована и проверена; теперь её сессионный аудит входит в общий LogService вместе с upload. Операционное подтверждение работы аудита на всех обслуживающих workers после rollout остаётся открытым. По прямому поручению пользователя от 2026-10-05 прежнее требование подтверждать и задавать даты начала coverage отменено: такие даты больше не являются условием численных метрик или включения. Локальная приёмка не подтверждает deployment; рабочая `.env` не менялась.
- Переход к фазе 3 подтверждён пользователем, её код находится в состоянии code_ready; первый пункт о рабочей БД остаётся `[ ]`. Успешные pytest/flake8/mypy — исторические результаты фазы 3: проверялся локальный api_router без app.main/production lifespan; созданный для проверки контейнер фазы 3 остановлен, рабочие контейнеры не затрагивались.
- Фаза 4 завершена в коде и локальной верификации после одобренных общих auth/header-исправлений, регрессионных тестов и синхронизации документации. Историческая фаза 4 не меняла backend, рабочую `.env`, БД, миграции, индексы и тогдашние coverage-настройки. Её результаты сохранены как исторические; последующая унификация изменила контракт подсчёта и текст дашборда. Открытые production-пункты фаз 2–3 frontend-проверками не закрываются.

Третий выполнен частично: snapshot, сессионные операции и неизменность собственной тестовой схемы проверены, но production metadata и согласованный репрезентативный объём/критерии стоимости остаются открытыми. Перед остановкой того контейнера подтверждены пустая `public` и отсутствие тестовых схем; исторический контейнер фазы 5 остановлен по точному ID после проверки метки. ## Ограничения совместимости

- Эндпоинты внешнего API должны оставаться обратно совместимыми. Удаление или переименование эндпоинта является ломающим изменением для подключённых систем.
- Миграции БД должны быть обратимыми: каждая миграция содержит upgrade() и downgrade().
- Pydantic-схемы ответов внешнего API являются контрактом: удаление полей из существующих схем недопустимо.
- Согласованный план stats исключает изменения схемы `log`, новые индексы и миграции рабочей БД. Общий аудит `account.error` upload и `session.error` start/finish/ban использует существующий журнал и независимый механизм LogService. Бизнес-commit, ответы, lifecycle/status-аудит и attempts сохранены; обычные post-commit cleanup/success-logger ошибки upload сохраняют HTTP 201, несколько ошибок запроса — один operation UUID. Legacy-логирование остальных account-эндпоинтов и побочный эффект повторного ban сохраняются. Не-HTTP ошибки классифицируются как `ERROR`, HTTP 404 — `NOT_FOUND`, остальные 4xx — `FAILURE` только в общем аудите; auth/message не переклассифицированы.
- Одобренные исправления shared auth/header сохраняют синхронные helpers, четыре поля token и объектный `window.isAuth`, lowercase `bearer` и legacy timestamps без timezone. Backend авторизации не менялся; credential caches остальных legacy grids не рефакторились. Защита свежести token в DashboardApi и общем auth poll не означает обновление всех прежних frontend-потребителей.
