# Ограничения проекта

## Технические ограничения

- Runtime — Python 3.11, совместимость с более ранними версиями не поддерживается
- Все I/O операции должны быть асинхронными (async/await), синхронные блокирующие вызовы запрещены в обработчиках запросов
- PostgreSQL является единственным поддерживаемым основным хранилищем, замена на другую СУБД не предусмотрена
- Файлы аккаунтов хранятся на локальной файловой системе (`upload/wa/`), что ограничивает горизонтальное масштабирование без внешнего object storage

## Архитектурные ограничения

- Зависимости между слоями направлены внутрь: обработчик → CRUD/сервис → модель → адаптер БД. Обратные зависимости запрещены.
- Доступ к базе данных осуществляется преимущественно через CRUD-слой. Сохраняется исключение для сложной логики с блокировками (FOR UPDATE SKIP LOCKED во внешнем API); пользователь также одобрил узкое исключение только для read-only аналитических SELECT внутри `StatsService` (`app/services/stats.py`).
- Для stats согласованы зависимости API → StatsService → существующий CRUD пользователя для scope / SQLAlchemy и адаптер БД для агрегатов. Отдельный пакет запросов и CRUD статистики не создаются. StatsService не допускает мутаций, записывающих SQL, `FOR UPDATE` и commit; исключение для аналитики не распространяется на остальные сервисы.
- Основная бизнес-логика на текущем этапе находится в обработчиках API. StatsService реализует период, область доступа, summary/live и coverage; stats API зарегистрирован через api_router. Каждый агрегат читается одним CTE SELECT, значения связаны параметрами, SQL-формы scoped/admin-all выбираются сервером. Массовое выделение остальной бизнес-логики в сервисы остаётся отдельной задачей рефакторинга.
- Для изменяющих операций коммит транзакции управляется обработчиком: CRUD-операции вызываются с `commit=False`, коммит — явно в обработчике.
- Реализованный SessionErrorAudit не содержит прямого SQL: независимая запись session.error идёт через существующий LogService.record_independent с собственной сессией и commit только после подтверждённого освобождения бизнес-транзакции. StatsService остаётся read-only; новые FK запрещены при неподтверждённом commit, ссылки на чужие сущности не сохраняются.
- SQLAlchemyError статистики обрабатывается локальным _StatsRoute, включая auth-зависимости, с общим 503 и безопасной диагностикой вне event loop. Глобальный middleware и обработка остальных маршрутов не менялись. Общий UTCDateTime располагается в core и используется settings/DTO без обратного импорта верхних слоёв.
- Дашборд получает бизнес-агрегаты через `DashboardApi` и фиксированные GET stats/options; клиент не воспроизводит SQL-расчёты, сохраняет `null` и отдельную семантику cohort. Явный `?demo=1` выбирает mock без stats/options-трафика, но с общей авторизацией; ошибки API не разрешают неявный fallback на вымышленные данные.

## Инфраструктурные ограничения

- Сервис запускается в Docker-контейнере на базе python:3.11
- Секреты передаются через переменные окружения, не хранятся в коде или Docker-образе
- Nginx обслуживает статические файлы из `html/` и проксирует запросы к API
- Планировщик APScheduler работает в том же процессе, что и API-сервер — при масштабировании на несколько worker'ов задачи будут дублироваться
- Проверки stats и session.error используют отдельную PostgreSQL 12 с явными `STATS_TEST_POSTGRES_DSN` и `STATS_TEST_ALLOW_SCHEMA_CREATE=1`. До DDL fixtures проверяют адрес `127.0.0.1` с портом, отличным от 5432, выделенные БД `o3go_stats_test` и пользователя `stats_test`, PostgreSQL 12, пустую `public` и отсутствие других пользовательских схем.
- В `tests/integration/conftest.py` существуют два режима изоляции: внешняя транзакция с rollback для stats и фиксируемая схема `stats_test_<uuid>` для реальных независимых соединений и commit. Второй режим после повторных проверок защиты удаляет через `DROP SCHEMA ... CASCADE` только созданную тестом UUID-схему; рабочая БД и `public` не удаляются. Оба режима и conftest на фазе 3 не менялись; ANALYZE перед EXPLAIN выполнялся только на тестовых таблицах, а сами агрегаты дополнительно проверены в `SET TRANSACTION READ ONLY` без commit.
- Тестовая PostgreSQL не подтверждает схему, индексы, объёмы и coverage рабочей БД. Пользователь подтвердил завершение фазы 1 по уточнённому объёму и перенос этой проверки в фазу 3: нужен явно предоставленный read-only endpoint либо операторский вывод. Проверки выполнялись с `env -i` из разрешённого временного CWD, без чтения рабочей `.env`, с фиктивным DSN приложения на порту 1; production-конфигурация не менялась.
- Кодовая часть фазы 2 реализована и проверена, но дата фактического начала production-учёта session.error неизвестна. Последний пункт фазы 2 остаётся открытым до rollout на всех обслуживающих workers и подтверждения оператором; одобрение локальной фазы 5 не разрешает deployment. `STATS_COVERAGE_STARTS` реализована с default `{}` и UTC-aware значениями только четырёх групп; explicit null отклоняется. В `.env.example` добавлен пустой объект, рабочая `.env` не менялась. Дата реализации кода не заменяет начало coverage; неизвестный учёт сохраняется как NULL, без фиктивных дат и backfill.
- Переход к фазе 3 подтверждён пользователем, её код находится в состоянии code_ready; первый пункт о рабочей БД остаётся `[ ]`. Успешные pytest/flake8/mypy — исторические результаты фазы 3: проверялся локальный api_router без app.main/production lifespan; созданный для проверки контейнер фазы 3 остановлен, рабочие контейнеры не затрагивались.
- Фаза 4 завершена в коде и локальной верификации после одобренных общих auth/header-исправлений, регрессионных тестов и синхронизации документации. В фазе 4 не менялись backend, рабочая `.env`, БД, миграции, индексы и даты coverage; `STATS_COVERAGE_STARTS={}` сохраняет неизвестный охват. Открытые production-пункты фаз 2–3 не закрываются frontend-проверками; результаты фазы 4 сохранены как исторические.
- Пользователь явно одобрил фазу 5; локальная приёмка завершена, первые два пункта выполнены. Третий выполнен частично: snapshot, сессионные операции и неизменность собственной тестовой схемы проверены, но production metadata и согласованный репрезентативный объём/критерии стоимости остаются открытыми. Четвёртый пункт о rollout не выполнен; общая реализация остаётся `in_progress`. Изменения фазы ограничены новыми тестами, операторским runbook и документационным сопровождением; runtime-код, конфигурация БД, рабочая `.env`, миграции, индексы и coverage-даты сохранены.
- Новая Python-приёмка фазы 5 охватывает явно перечисленные в плане файлы stats/session.error и смежных регрессий, а не весь репозиторий. Она выполнена на отдельной PostgreSQL 12.22 из разрешённого временного CWD с `env -i`, без чтения рабочей `.env`, с фиктивным DSN приложения на порту 1 и отдельным loopback-портом тестовой БД. Защитный conftest и оба режима fixtures сохранены; фиксируемая UUID-схема повторно использована для независимых commit. Перед остановкой подтверждены пустая `public` и отсутствие тестовых схем; собственный контейнер без mounts, с tmpfs, остановлен по точному ID после проверки метки. Идентификаторы, параметры и артефакты записаны в плане.
- Конкурентная snapshot-проверка использует тестовую advisory CTE вокруг неизменённого SELECT с типизированными binds; `pg_locks` подтверждает ожидание через commit writer. Следующий SELECT без обёртки видит commit в той же READ COMMITTED-транзакции. Отдельная проверка настоящих start/finish/повторного ban вызывает обработчики напрямую и читает stats без обёртки при приостановленном перед commit writer. Это не приёмка HTTP/auth-конкурентности или нагрузочного SLA. Каталоги сравниваются только до/после внутри собственной UUID-схемы; совпадение таблиц, колонок/defaults, индексов и ограничений не подтверждает production parity.
- EXPLAIN фазы 5 повторён на прежнем синтетическом наборе с ANALYZE только тестовых таблиц. Эти объёмы не согласованы как репрезентативные для production; замеры не задают SLA. Одновременный локальный browser-прогон также исключает интерпретацию новых и архивных времён как сопоставимого performance benchmark; точные значения и команды находятся в плане.
- `plans/261003-dashboard-backend/rollout.md` подготовлен, но не выполнен и не является разрешением на deployment. В нём зафиксированы фактические особенности запуска: startup `init_db` с флагами создания/удаления таблиц и проверкой/созданием superuser, scheduler в каждом worker, безусловная регистрация stats без отдельного feature flag и влияние bind mounts на версию релиза. `STATS_COVERAGE_STARTS={}` не отключает stats UI/API. Фактические окружение, адреса/порты, эффективные startup-флаги, топология workers и способ ограничения доступа должны быть подтверждены оператором.
- Для завершения операционных пунктов нужны явно разрешённый read-only endpoint либо обезличенные metadata рабочей БД, включая историю/retention, согласованные объёмы и численные критерии стоимости, разрешённый релиз с проверенным откатом и окружением, подтверждение аудита на всех обслуживающих workers и основания coverage по группам. Согласие на фазу 5 и подготовка runbook этих сведений не заменяют; deployment не выполнялся.
- Browser-проверки фаз 4–5 выполнялись только в Chromium 153.0.8010.12 с фактическими jQuery 1.12.4/Kendo 2022.2.510 и HTTP/clock fixtures, без production API; полный повторный прогон фазы 5 прошёл. BFCache/storage проверены синтетическими `PageTransitionEvent`/`StorageEvent`, а не реальным history traversal или межвкладочной доставкой; drill-down проверен вызовом Kendo `seriesClick`, а не pointer hit-testing SVG. Firefox/WebKit не проверялись.
- Frontend-проверки используют встроенный Node test runner и внешний Playwright без новых зависимостей или установки пакетов в проект. `DASHBOARD_SCREENSHOTS` принимает только существующий системный временный каталог вне репозитория; отчёт и screenshots являются локальными тестовыми артефактами, не конфигурацией приложения.

## Ограничения совместимости

- Эндпоинты внешнего API должны оставаться обратно совместимыми. Удаление или переименование эндпоинта является ломающим изменением для подключённых систем.
- Миграции БД должны быть обратимыми: каждая миграция содержит upgrade() и downgrade().
- Pydantic-схемы ответов внешнего API являются контрактом: удаление полей из существующих схем недопустимо.
- Согласованный план stats исключает изменения схемы `log`, новые индексы и миграции рабочей БД. Аудит `session.error` реализован в существующей структуре журнала через SessionErrorAudit и независимый механизм LogService. Бизнес-commit, ответы, lifecycle/status-аудит и attempts сохранены; исправление побочного эффекта повторного ban остаётся вне scope.
- Одобренные исправления shared auth/header сохраняют синхронные helpers, четыре поля token и объектный `window.isAuth`, lowercase `bearer` и legacy timestamps без timezone. Backend авторизации не менялся; credential caches остальных legacy grids не рефакторились. Защита свежести token в DashboardApi и общем auth poll не означает обновление всех прежних frontend-потребителей.
