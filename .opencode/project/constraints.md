# Ограничения проекта

`status: complete` обозначает полноту документации, а не завершённый релиз. Синхронизация спецификаций одобрена пользователем 2026-10-12; разрешения на deployment это не даёт.

## Технические ограничения

- Runtime — Python 3.11, совместимость с более ранними версиями не поддерживается
- Все I/O операции должны быть асинхронными (async/await), синхронные блокирующие вызовы запрещены в обработчиках запросов
- PostgreSQL является единственным поддерживаемым основным хранилищем, замена на другую СУБД не предусмотрена
- Файлы аккаунтов хранятся на локальной файловой системе (`upload/wa/`), что ограничивает горизонтальное масштабирование без внешнего object storage

## Архитектурные ограничения

- Зависимости между слоями направлены внутрь: обработчик → CRUD/сервис → модель → адаптер БД. Обратные зависимости запрещены.
- Доступ к базе данных осуществляется преимущественно через CRUD-слой. Сохраняется исключение для сложной логики с блокировками (FOR UPDATE SKIP LOCKED во внешнем API); пользователь также одобрил узкое исключение только для read-only аналитических SELECT внутри `StatsService` (`app/services/stats.py`).
- Для stats согласованы зависимости API → StatsService → существующий CRUD пользователя для scope / SQLAlchemy и адаптер БД для агрегатов. Отдельный пакет запросов и CRUD статистики не создаются. StatsService не допускает мутаций, записывающих SQL, `FOR UPDATE` и commit; исключение для аналитики не распространяется на остальные сервисы.
- Основная бизнес-логика на текущем этапе находится в обработчиках API. StatsService реализует период, область доступа, summary/live и coverage; stats API зарегистрирован через api_router. Каждый агрегат читается одним CTE SELECT, значения связаны параметрами, SQL-формы scoped/admin-all выбираются сервером. Массовое выделение остальной бизнес-логики в сервисы остаётся отдельной задачей рефакторинга.
- Для изменяющих операций коммит транзакции управляется обработчиком: CRUD-операции вызываются с `commit=False`, коммит — явно в обработчике.
- Account/file-аудит внешнего upload и административных account-операций, а также `session.error` start/finish/ban принадлежат `LogService`; `app/services/session_error.py` удалён. `LogOperation` — dataclass состояния отдельного запроса с явными action/source и nullable actor, без методов аудита. `flush_events` и `report_error` подтверждают release бизнес-транзакции, затем используют `record_independent` с CRUD, собственной сессией и commit; прямого SQL в аудите нет. Их bool означает release, не успешность аудита. При неподтверждённом release latch блокирует следующие writers; новые FK разрешены только после подтверждённого business commit, чужие ссылки исключены.
- `queue_event` без I/O замораживает отдельный безопасный факт/target и db_outcome на момент наблюдения; transaction_released относится к финализации. Поздний business commit не переписывает файловый факт. Защищённое завершение дренирует весь буфер при повторной отмене, обычный отказ writer не теряет следующие факты; неизвестный audit commit не повторяется. Очередь в памяти не даёт общей атомарности filesystem/БД, crash-durability или exactly-once.
- Административный DELETE подтверждается узким CRUD DELETE RETURNING и фиксируется атомарно с `account.delete`; отсутствие RETURNING не считается удалением. Delete и связанные file/error события имеют NULL доменные FK и target в details. Bulk сохраняет отдельные snapshots и один operation UUID, пропускает повторные ID до I/O; файловые writers ждут release. Старые CASCADE/retention не меняются. Member logs по-прежнему фильтруется по текущему владельцу связанного account: NULL-FK строка может учитываться в actor-summary, но не показываться в его журнале.
- Profile-only действия и их ошибки не создают новых DB-событий; техническая диагностика и cancellation сохраняются. Намеренный пропуск writer не является audit_unavailable. Успешные GET account-маршрутов не аудируются и не вызывают commit ради журнала; охвачены только ошибки внутри обработчика, не ошибки auth/multipart/валидации зависимостей до него. Архивная ошибка не дублируется общим account.error; отсутствие архива при cleanup — skip, при явном standalone remove — прежний 404/file.delete.error.
- Защищённое завершение аудита сохраняет первичную ошибку и внешнюю отмену до очистки зависимостей. Минимальный stderr fallback обязателен при неподтверждённом аудите, включая неожиданный отказ finalizer/защищённой задачи и обычную post-commit ошибку upload с ответом 201; отказ stderr отмечается в исходном исключении. Общая диагностика ограничивает строки 160 символами, обход причин и traceback — 12 элементами, исключает raw exception messages, SQL/параметры и произвольные OS paths. Upload помещает разрешённые метаданные, включая `number`, `info_1..info_8` и storage/cleanup, только в `details`; hash-значения, headers и содержимое файлов исключены. Сессионный аудит не передаёт request-details.
- Summary читает только log и применяет actor-предикат `log.user_id` до агрегации/MIN; live использует текущего владельца account. NULL actor включается только в admin-all. Success-счётчики считают точные события без новых source/FK/action/operation_id ограничений; legacy context={} допустим. Три account-error группы принимают api/ext_api, session.error — только ext_api; дедупликация идёт по event/source/user/operation_id с global-first до нижней границы периода. Сумма категорий ошибок не равна числу уникальных неуспешных запросов.
- `STATS_COVERAGE_STARTS`, её типы/валидатор и пример `.env.example` удалены; `get_summary` не принимает `coverage_starts`. DTO требует 17 nullable-метрик в totals/previous/каждой точке и семь coverage-групп с `from: null`; `recorded` означает подсчитываемость, не полноту сбора, ноль — отсутствие записанных событий. Только отсутствующий, JSON null или пустой operation_id даёт partial/missing_operation_id и маскирует соответствующую одну из четырёх error-групп всего затронутого периода и его buckets; другой период/группы сохраняют числа. Gap/count source-предикаты совпадают. `closed` считается SQL как finished + session_bans без повторного auto_finished. Ручных дат, backfill, cohort/message_created/доставляемости в текущем DTO нет; UTC/месяц, message-first и независимый live сохранены.
- SQLAlchemyError статистики обрабатывается локальным _StatsRoute, включая auth-зависимости, с общим 503 и безопасной диагностикой вне event loop. Глобальный middleware и обработка остальных маршрутов не менялись. Общий UTCDateTime сохранён в core для DTO и проверки UTC-контрактов без обратного импорта верхних слоёв; удаление coverage-settings не удаляет этот тип.
- DashboardApi принимает обязательный контракт 17/7 через фиксированные GET stats/options; клиент не воспроизводит SQL-расчёты, включая closed, и сохраняет null. UI содержит 12 карточек и шесть графиков; график сообщений, его четыре серии и failed без отдельной карточки сохранены. Фильтр журнала имеет 19 вариантов event, но чтение произвольных строковых событий не ограничено whitelist. Явный `?demo=1` выбирает mock без stats/options-трафика, с общей авторизацией; ошибка API не включает вымышленные данные.
- UI объясняет сохранённую историю и нули, сохраняет quality-warning/null и не представляет legacy coverage.from как гарантированную дату сбора. Ссылка на дашборд видима для admin/member, прямой `/dashboard/` доступен; скрытие ссылки не ограничивает API. Видимая навигация, log-only основа и пользовательские auth/CSS/live-правки уже существовали в baseline и не являются результатом account/file-задачи. Guards credentials/revision/scope/period, независимость live и общая авторизация сохранены.

## Инфраструктурные ограничения

- Сервис запускается в Docker-контейнере на базе python:3.11
- Секреты передаются через переменные окружения, не хранятся в коде или Docker-образе
- Nginx обслуживает статические файлы из `html/`; в текущем `services/nginx.conf` нет действующего API proxy. Адрес API выбирает общий frontend, фактическая production-маршрутизация требует операторских сведений.
- Планировщик APScheduler работает в том же процессе, что и API-сервер — при масштабировании на несколько worker'ов задачи будут дублироваться
- Проверки stats и account/file/session-аудита используют отдельную PostgreSQL 12 с явными `STATS_TEST_POSTGRES_DSN` и `STATS_TEST_ALLOW_SCHEMA_CREATE=1`. До DDL fixtures проверяют адрес `127.0.0.1` с портом, отличным от 5432, выделенные БД `o3go_stats_test` и пользователя `stats_test`, PostgreSQL 12, пустую `public` и отсутствие других пользовательских схем.
- В `tests/integration/conftest.py` существуют два режима изоляции: внешняя транзакция с rollback для stats и фиксируемая схема `stats_test_<uuid>` для реальных независимых соединений и commit. Второй режим после повторных проверок защиты удаляет через `DROP SCHEMA ... CASCADE` только созданную тестом UUID-схему; рабочая БД и `public` не удаляются. Оба режима и conftest на фазе 3 не менялись; ANALYZE перед EXPLAIN выполнялся только на тестовых таблицах, а сами агрегаты дополнительно проверены в `SET TRANSACTION READ ONLY` без commit.

## Ограничения совместимости

- Эндпоинты внешнего API должны оставаться обратно совместимыми. Удаление или переименование эндпоинта является ломающим изменением для подключённых систем.
- Миграции БД должны быть обратимыми: каждая миграция содержит upgrade() и downgrade().
- Pydantic-схемы ответов внешнего API являются контрактом: удаление полей из существующих схем недопустимо.
- Согласованный объём исключает изменения схемы log, новые индексы и миграции. Account/file/session-аудит использует существующие строковые events/source и JSONB context; физическая production-схема должна уже поддерживать необходимые nullable FK. Бизнес-commit, HTTP-контракты, lifecycle/status и attempts сохранены, включая повторный ban и обычный post-commit HTTP 201 upload. Не-HTTP ошибки относятся к ERROR, HTTP 404 — NOT_FOUND, остальные 4xx — FAILURE только в общем LogService-аудите; auth/message не переклассифицированы.
- Q1 сохраняет account.update внешнего upload, административного PUT без status и обоих прежних hash-маршрутов; PUT с присутствующим status выбирает account.status даже без изменения значения. Hash-helper не переработан. Q2 сохраняет отсутствие обязательного JWT у standalone accounts/upload и /remove, поля формы и ответы; новый actor всегда NULL, не выводится из body, имени файла, владельца или непроверенных credentials. Архивный widget и профильные endpoints не подключены к новому auth/аудиту.
- Старые account.error не переклассифицируются по stage, новые файловые группы не восстанавливаются из create/update. Исторический account.error/api теперь учитывается как разрешённый источник; это расширение охвата, не перенос ошибок в другую категорию. Старые context={} и произвольные строковые event остаются читаемыми; старый FK-CASCADE и права чтения журнала не меняются. Новый контракт 17/7 требует согласования версий backend/UI, несмотря на совместимость со старой историей.
- Одобренные исправления shared auth/header сохраняют синхронные helpers, четыре поля token и объектный `window.isAuth`, lowercase `bearer` и legacy timestamps без timezone. Backend авторизации не менялся; credential caches остальных legacy grids не рефакторились. Защита свежести token в DashboardApi и общем auth poll не означает обновление всех прежних frontend-потребителей.
