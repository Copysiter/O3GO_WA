## Структура проектной документации

Контекст проекта располагается в `.opencode/project/` в виде восьми markdown-файлов. Каждый файл описывает отдельный аспект системы и служит справочным материалом для разработчиков и AI-агентов:

| Файл | Назначение | Приоритет |
|------|-----------|-----------|
| `overview.md` | Идентичность проекта: что это, зачем существует, тип системы, ключевые технологии | Высокий — читать первым |
| `architecture.md` | Структурный дизайн: слои, компоненты, границы ответственности, поток запросов | Высокий |
| `stack.md` | Технологические решения: runtime, фреймворки, хранилища, messaging, auth, тестирование | Высокий |
| `structure.md` | Структура репозитория: директории, организация кода, навигационные рекомендации | Средний |
| `conventions.md` | Инженерные стандарты: принципы, стиль кода, именование, ожидания по тестированию | Средний |
| `constraints.md` | Границы: технические, архитектурные, инфраструктурные ограничения и требования совместимости | Средний |
| `integrations.md` | Внешние зависимости: системы, протоколы, расположение адаптеров, заметки по надёжности | Средний |
| `changes.md` | Changelog документации: фиксирует изменения контекста проекта с течением времени | Низкий — только дополнение |

Шаблоны для этих файлов расположены в `.opencode/templates/project/`.

## Рекомендации по загрузке контекста

Различные задачи требуют различных подмножеств проектной документации. Загрузка нерелевантных файлов расходует контекстное окно без пользы:

**Планирование и архитектурная работа:**
overview.md, architecture.md, stack.md, conventions.md, constraints.md

**Реализация:**
overview.md, architecture.md, conventions.md, constraints.md, integrations.md

**Код-ревью:**
overview.md, architecture.md, conventions.md, constraints.md

**Ориентационные вопросы:**
overview.md, stack.md

**Работа с интеграциями:**
overview.md, integrations.md, stack.md

## Правила обновления документации

Настоящие правила распространяются на все модификации проектных файлов без исключения:

1. **Подтверждение перед перезаписью.** Представить предлагаемые изменения пользователю и получить явное одобрение перед записью в любой проектный файл.

2. **Дополнение вместо замены.** При обновлении файла интегрировать новую информацию с существующим содержимым. Секции, не затронутые обновлением, должны оставаться без изменений.

3. **Приоритет ручных правок.** Контент, написанный или доработанный человеком, имеет приоритет над сгенерированным текстом. Перезаписывать его допустимо только по явному запросу пользователя.

4. **Техническая ясность.** Исключать избыточную многословность, избегать спекулятивных утверждений, формулировать мысли точным инженерным языком. Соблюдать ограничения формата, унаследованные от guide'ов шаблонов.

5. **Фиксация каждого структурного изменения.** После модификации любого проектного файла добавить запись в `.opencode/project/changes.md` с указанием даты, характера изменения и его обоснования.

6. **Межфайловая согласованность.** При обновлении одного файла проверить, что связанные файлы не содержат противоречащих утверждений. Например, изменение базы данных в stack.md не должно конфликтовать с описанием в architecture.md или integrations.md.

## Формат changes.md

Новые записи размещаются в начале файла в обратном хронологическом порядке:

```markdown
## YYYY-MM-DD

### Добавлено
- описание нового контента

### Изменено
- описание модифицированного контента

### Причина
Обоснование данного изменения.
```

## Правила валидации

При оценке качества проектной документации классифицировать находки по степени серьёзности:

### Критические проблемы (требуют обязательного исправления)
- Обязательные секции остались пустыми при `status: complete` во frontmatter
- Оставшиеся маркеры `{{placeholder}}` в финализированных документах
- Оставшиеся блоки `[TEMPLATE_GUIDE]` или `[TEMPLATE_EXAMPLE]`
- Фактические противоречия между файлами (например, stack.md указывает PostgreSQL, а architecture.md ссылается на MongoDB)

### Предупреждения (желательно устранить)
- Опциональные секции оставлены пустыми без обоснования
- Пути к директориям, упомянутые в документации, но отсутствующие в реальном репозитории
- Точки интеграции, присутствующие в коде, но не отражённые в integrations.md
- Документация не обновлялась более трёх месяцев

## Frontmatter файлов

Каждый проектный файл содержит YAML frontmatter, отслеживающий происхождение шаблона и состояние обработки:

```yaml
---
template: overview
version: 1
status: complete        # empty | partial | complete
updated: "2026-01-15"
required_sections: [...]
optional_sections: [...]
---
```

Обновлять `status` и `updated` после каждого изменения контента.

## Языковая политика

- Отвечать на том же языке, который использует пользователь в своём сообщении
- Не переводить контент автоматически без явного запроса
- Не смешивать языки в рамках одного ответа
- Пути к файлам, CLI-команды и ключи конфигурации сохранять на английском языке вне зависимости от языка ответа
- Сохранять английский для технических терминов, когда перевод снижает точность формулировки
